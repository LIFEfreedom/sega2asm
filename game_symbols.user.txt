; ── Блок таймеров, обновляется в VBlank ($000430) ─────────────────────
; Обработчик берёт базу `lea ($FF005A).l,a0` и идёт по блоку через (a0)+,
; поэтому все четыре лежат подряд именно в этом порядке.

FrameWait        = $FF005C   ; word, +1 каждый кадр. Идиома по всему коду:

                             ; Сравнивается с #$BB8 (3000 кадров ≈ 50 с)

; ── Инициализация ($0008F8) ───────────────────────────────────────────
; Теневая копия регистров VDP: цикл на 19 итераций читает значения из ROM,

VDPRegShadow     = $FF0018

; ── Точки входа BIOS игры (вызываются через line-F трапы) ─────────────
; Аргументы кладутся на стек вызывающим; обработчик читает их по a6,
; который диспетчер настраивает на кадр вызова.

; $FF10 — Decompress(dest, src). Сам диспетчер: байт +2 заголовка блока
; выбирает метод из таблицы $000D5A (7 записей, смещения относительно
; себя). ИСПРАВЛЕНО: раньше здесь стояло «почти всегда метод 7» — это была
; ошибка выборки. По полному индексу все 1629 блоков игры сжаты МЕТОДОМ 1.
; Метод 1 = $000D68, сверен с compress/lz_cri.go и совпадает до деталей,
; включая старт потока на +$3 (`addq.l #1,a5` после чтения размера).
DecompressM1             = $000D68   ; метод 1: LZ77, длина 7 бит, расстояние байтом
DecompressM2             = $000DF8   ; метод 2: словарь плюс унарный код, без ссылок
DecompressM3             = $000E98   ; метод 3: LZ77, бит 6 токена включает расстояние словом
DecompressM6             = $0011B0   ; метод 6: адаптивный Хаффман плюс ссылки, блоками
DecompressM7             = $000F3A   ; метод 7: словарь и унарный код плюс ссылки, блоками
BiosDecompress           = $000D42   ; трап $FF10: метод из байта +$2 заголовка,
                             ; прыжок по data_12 = $000D5A; методов пять, 4 и 5 не существуют

; $FF25 — вывод в таблицу имён: $0(a6) атрибут, который OR-ится в каждую

; Массив юнитов: записи по $30 (48) байт, индекс — БАЙТ, то есть до 256
; штук. Размер доказан явным умножением:

; Остальной код считает то же идиомой ×48 = ×16 сохранить, ×32, сложить:
;   $017E80: lsl.w #4,d1 / move.w d1,d3 / lsl.w #1,d1 / add.w d3,d1
; Смещения внутри записи: +$02/+$03 клетка X/Y, +$07 состояние (анимация),
; +$09 владелец (>0 игрок 1, <0 игрок 2, =0 ничей), +$16 ТЕКУЩИЕ HP (word),
; +$18 смещение в UnitStatTable, +$1C биты порогов HP, +$28 битовые флаги.

; Таблица дескрипторов: в каждой записи по смещению 0 лежит указатель на
; блок параметров. Индексируется напрямую байтовым смещением из +$18(юнит):
;   lea ($01FC5A).l,a4 / move.w $18(a2),d7 / lea ($0,a4,d7.w),a4
;   movea.l $0(a4),a4  / move.w $4(a4),$16(a2)

; Доказательство: +$04 копируется в HP при полном восстановлении
; ($01D214), +$06 и +$08 сравниваются с текущим HP и задают биты 0 и 1
; байта +$1C ($01D276, $01D28E).

; Бит 5 байта +$11 записи юнита проверяется 18 раз, ставится РОВНО ОДИН РАЗ
; и не снимается нигде. Он переключает вторую половину блока параметров.

; Раскладка блока параметров сошлась ровно в $146 (326) байт:
;   +$000..+$039  58  общие скаляры (макс HP +$04, пороги +$06/+$08)
;   +$03A..+$04F  22  таблица A, обычная
;   +$050..+$07B  44  таблица B, обычная
;   +$07C..+$0A1  38  таблица C, обычная
;   +$0A2..+$0D7  54  скаляры парами обычное/улучшенное
;   +$0D8..+$0ED  22  таблица A, улучшенная   (сдвиг $9E от обычной)
;   +$0EE..+$119  44  таблица B, улучшенная   (тот же сдвиг)
;   +$11A..+$13F  38  таблица C, улучшенная   (тот же сдвиг)
;   +$140..+$145   6  хвост
; Пары скаляров: +$AC/+$AD (шанс редкого исхода боя), +$B2/+$B3,
; +$C2/+$C3, +$CE/+$D2 и +$D0/+$D4 (пороги размножения).
; Улучшение поднимает шанс сильного удара с 1/256 (0.4%) примерно до 19%.

; Номера эффектов в ActiveEffectCode продолжают ряд без пропусков:
;   1..7 погода, 8..13 яйца, 14..17 растения, 18..23 эта команда.

; ВНИМАНИЕ, асимметрия в коде. В ветке улучшения оба обработчика берут вид
; из GetUnitSpecies (нумерация с единицы), но первый делает `subq.w #1,d7`
; перед индексацией CostsRemodel2, а второй — нет. Второй поэтому берёт
; цену на одну запись дальше. Соседняя ветка (превращение в другой тип,
; CostsRemodel) у обоих индексируется одинаково, так что на разные
; соглашения о нумерации меню не спишешь. Похоже на ошибку, но достижимость
; второй ветки на практике я НЕ проверял.

; Урон = сила нападающего по степени × коэффициент цели / 256.
; Степень берётся из СОСТОЯНИЯ получающего ($14..$17 -> индекс 0..3), а НЕ
; из поля +$29. Поправка к docs/game-actions.md: +$29 записывается вместе с

; Поля блока параметров, опознанные в этом заходе:
;   +$0A,+$0C,+$0E,+$10   сила удара по степеням 0..3 (обычная)
;   +$C4,+$C6,+$C8,+$CA   то же для улучшенного юнита
;   +$AE / +$AF           коэффициент получаемого урона, из 256;
;                         меньше — лучше. Лучший у ﾄﾘｹﾗ (155), худший
;                         у ﾋﾟｰﾁｬﾝ (255)
;   +$50 / +$EE           таблица B: урон по типу местности, состояние $32
;   +$7C / +$11A          таблица C: то же для состояния $0F
; Редкая степень 3 даёт 1300..2500 при запасе здоровья 1000..2200, то есть

; Улучшение поднимает шанс редкой степени до 12..19% и силу обычных, но
; СНИЖАЕТ силу редкой. Ожидаемый урон растёт в 1.6 раза у сильных видов и
; в 3.3..4.4 у слабых: улучшение подтягивает отстающих.
; Распределение обычных степеней: 37.9% / 48.4% / 13.7%.
; В таблицах местности значение 9999 (больше любого запаса здоровья)
; стоит на типах 11, 12, 13 и 20 — эта местность убивает на месте.

; Все пути «этого не должно случиться» ведут сюда. Процедура целиком:
;   nop / nop / rts — узнаваемая форма отладочной точки останова,
; оставленной в релизе. Вызовов 29: переполнение пула слотов, индекс вида
; больше девяти, тип местности вне таблицы и прочее. Выполнение после неё
; продолжается, то есть ошибки проглатываются молча.
