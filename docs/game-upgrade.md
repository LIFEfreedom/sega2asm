# Бит 5 байта `+$11` — постоянное улучшение

Бит проверяется 18 раз по всему коду, **ставится ровно один раз** и не
снимается нигде. Он переключает вторую половину блока параметров вида.

## Кто его ставит

```asm
; $01E6EA
	movem.l	d0,-(a7)
	bset	#5,$11(a2)
	move.l	a2,d0
	subi.l	#$00FF5F4E,d0     ; номер юнита в байтах от базы массива
	jsr	(loc_00C664).l    ; сообщить об изменении
	movem.l	(a7)+,d0
	rts
```

Вызывается из обработчика платной команды, который сначала проверяет
деньги и списывает их. Цена берётся из таблицы `$0223A4` по виду юнита.

Тот же обработчик умеет и другое: при индексе меню 0 он ставит бит 5, а
при 1…6 превращает юнита в тип из таблицы в `MainState` через `RemodelUnit`
`$01E708`. Номер эффекта при этом — индекс плюс `$12`, то есть `$12`…`$17`.

Это продолжает ряд, найденный раньше: **1–7 погода, 8–13 яйца, 14–17
растения, 18–23 эта команда**. Четыре меню подряд, без пропусков.

## Что бит 5 меняет

Не один параметр, а целую параллельную половину блока. Смещение табличных
полей — ровно `$9E` (158):

| обычное поле | при бите 5 | что это |
|---|---|---|
| `+$3A` | `+$D8` | таблица A, 22 байта |
| `+$50` | `+$EE` | таблица B, 44 байта |
| `+$7C` | `+$11A` | таблица C, 44 байта |

Скаляры лежат парами рядом, а не со сдвигом:

| обычное | при бите 5 | где используется |
|---|---|---|
| `+$AC` | `+$AD` | шанс редкого исхода боя (`ResolveCombat`) |
| `+$B2` | `+$B3` | ещё один бросок, `$01AE52` |
| `+$C2` | `+$C3` | `$0192FE`, `$01949A` |
| `+$CE` | `+$D2` | порог размножения |
| `+$D0` | `+$D4` | порог размножения |

## Раскладка блока сходится ровно

Из трёх пар табличных смещений и длины блока `$146` (326 байт) получается
полная раскладка без остатка:

| смещение | байт | что |
|---|---|---|
| `+$000`…`+$039` | 58 | общие скаляры: макс HP `+$04`, пороги `+$06`/`+$08` |
| `+$03A`…`+$04F` | 22 | таблица A, обычная |
| `+$050`…`+$07B` | 44 | таблица B, обычная |
| `+$07C`…`+$0A7` | 44 | таблица C, обычная |
| `+$0A8`…`+$0D7` | 48 | скаляры парами обычное/улучшенное |
| `+$0D8`…`+$0ED` | 22 | таблица A, улучшенная |
| `+$0EE`…`+$119` | 44 | таблица B, улучшенная |
| `+$11A`…`+$145` | 44 | таблица C, улучшенная |

Сумма — ровно 326, и **хвоста не остаётся**: блок кончается там же, где
кончается улучшенная таблица C. Раскладка выведена из кода, а сошлась с
независимо измеренным шагом блоков; это хорошая проверка обеих величин.

Раньше здесь стояло, что таблица C — 38 байт (19 слов), а в конце блока
лежит шесть байт хвоста. Обе цифры были ошибкой: C такая же, как B, 22
слова, и три последних столбца просто не попадали в разбор
([game-terrain.md](game-terrain.md)).

Сравнение половин у вида 3 (ｱﾛ) показывает, что улучшенные значения
действительно лучше:

```
таблица A обычная:   12 14 16 18 1a 14 15 16 28 28 14 ...
таблица A улучшенная: 0f 0f 10 11 12 0f 10 11 19 19 14 ...
```

Числа меньше — похоже на задержки или периоды.

## Насколько это сильное улучшение

Самое заметное — шанс редкого исхода в бою. У базовых видов `+$AC` равен
единице, то есть `1/256` = 0.4%. `+$AD` у тех же видов — 50, то есть 19.5%.
**Улучшение поднимает шанс сильного удара примерно в пятьдесят раз.**

| вид | цена улучшения | `+$AC` -> `+$AD` |
|---|---|---|
| 1 ｽﾃｺﾞ | 1133 | 0.4% -> 19.5% |
| 2 ﾄﾘｹﾗ | 1339 | 0.4% -> 19.5% |
| 3 ｱﾛ | 1854 | 0.4% -> 19.5% |
| 4 ﾃｨﾗﾉ | 2575 | 0.4% -> 17.6% |
| 5 ﾌﾟﾃﾗ | 2060 | 0.4% -> 12.5% |
| 6 ﾋﾟｰﾁｬﾝ | 1854 | 0.4% -> 19.5% |

Цены в BCD, из таблицы `$0223A4`. Дороже всех улучшать ﾃｨﾗﾉ.

## Асимметрия в цене между игроками

У команды два обработчика: `$0237DE` работает с текущим игроком через
`CanAfford`, `$023864` — отдельный, через `CanAffordP2`. В ветке улучшения
оба берут вид из одной и той же процедуры `$01E35A`:

```asm
; $01E35A
	move.b	$C(a2),d0
	andi.w	#$001F,d0         ; вид, нумерация с единицы
	rts
```

Дальше они расходятся:

```asm
; $023838 — первый обработчик
	bsr.w	loc_01E35A
	moveq	#0,d7
	move.b	d0,d7
	subq.w	#1,d7             ; ← есть
	lsl.w	#2,d7
	lea	$0223A4(pc),a5

; $0238A0 — второй обработчик
	bsr.w	loc_01E35A
	moveq	#0,d7
	move.b	d0,d7
	                          ; ← нет
	lsl.w	#2,d7
	lea	$0223A4(pc),a5
```

Источник индекса общий, нумерация видов с единицы, а вычитание есть только
в одном месте. Второй обработчик поэтому берёт цену на одну запись дальше:
за улучшение стегозавра платит цену трицератопса и так далее. Для вида 6
он уходит за конец таблицы — в следующую, где лежит 37.

Соседняя ветка той же процедуры (превращение в другой тип, таблица
`$02238C`) у обоих обработчиков индексируется **одинаково**, так что дело
не в разных соглашениях о нумерации меню.

**Осторожно:** это асимметрия в коде, а не наблюдённое поведение игры. На
ошибку похоже, но я не проверял, достижима ли вторая ветка на практике и с
какими видами.
