# Противники: откуда берутся, чем описаны, как думают

Короткий ответ на «где противники»: **они не лежат отдельным списком**.
Противник — такой же объект, как бочка или платформа, и порождается из
клетки карты. Отличает его только то, что его процедура обновления зовёт
систему урона.

## Откуда берутся

Цепочка та же, что у всех объектов:

```
байт свойств клетки  ->  таблица `+$20` записи уровня  ->  конструктор
                                                              |
                      +$1E процедура обновления  <------------+
                      +$22 скрипт анимации       <------------+
```

По всем 23 уровням клетки порождают **1945 объектов, 182 различных
конструктора, 81 различный первый кадр**. Поведение ВСЕХ объектов, а не
только противников, разобрано в [objects.md](objects.md): противники — это
19 % населения карт, а 56 % — украшение с пустой процедурой обновления.

## Описания как такового нет

Таблицы «вид противника -> жизни, урон, скорость» в игре не существует.
Описание противника — это **сам конструктор**, и параметры в нём стоят
непосредственными операндами. Вот три варианта жука, целиком:

```asm
loc_2A43E6:
	jsr	(loc_29974C).l          ; завести объект
	cmpa.w	#$0000,a0
	beq.w	loc_2A440A              ; не завёлся — выходим
	move.l	#$002A4A7A,$1E(a0)      ; процедура обновления
	move.l	#$001D8D82,$22(a0)      ; скрипт анимации
	bset	#0,$1(a0)
	rts
```

У всех трёх вариантов процедура обновления одна и та же, а скрипты разные —
то есть «виды» здесь различаются только анимацией.

## Система урона

Её ядро — `loc_2A2C48`, и зовут его почти все настоящие противники.
Параметры передаются в регистрах, а состояние лежит в записи объекта:

| поле | что |
|---|---|
| `+$A` | таймер неуязвимости, тикает вниз |
| `+$1C` | **очки жизни** |
| `+$42` | накопленный удар, байт |
| `+$44` | тип удара, слово |

```asm
loc_2A2C48:                      ; d1 = кадры неуязвимости, d2 = маска
	moveq	#0,d0
	tst.w	$A(a0)
	beq.s	loc_2A2C58
	subq.w	#1,$A(a0)        ; неуязвим — тикаем и
	clr.b	$42(a0)          ; забываем удар
loc_2A2C58:
	tst.b	$42(a0)
	beq.s	loc_2A2C7E       ; удара не было
	and.w	$44(a0),d2       ; тип удара против маски вида
	beq.s	loc_2A2C7E       ; не тот тип — не берёт
	moveq	#1,d0
	move.w	d1,$A(a0)        ; завели неуязвимость
	moveq	#0,d1
	move.b	$42(a0),d1
	clr.b	$42(a0)
	sub.w	d1,$1C(a0)       ; сняли жизни
	beq.s	loc_2A2C7C
	bpl.s	loc_2A2C7E       ; ещё жив
loc_2A2C7C:
	subq.w	#2,d0            ; d0 = -1: умер
loc_2A2C7E:
	clr.w	$44(a0)
```

Возврат в `d0`: `0` ничего не было, `1` попали, `-1` умер.

## Параметры видов

Их три, и все три — непосредственные операнды, а не запись в таблице:
жизни ставит конструктор в `+$1C`, а кадры неуязвимости и маску уязвимости
вызывающий кладёт в `d1` и `d2` прямо перед `bsr.w loc_2A2C48`.

**Противников — 34 конструктора из 182**, на них приходится 372 клетки.
Перепись по видам, с картинками, — в
[enemy-catalog.md](enemy-catalog.md) (`tools/enemies.py`).

Раньше здесь стояло «43 конструктора, 420 клеток». Это была грубая
прикидка: она считала противником и генератора, который сам не бьётся, а
только выпускает противников (`$29B6AC`, `$2A166A` и им подобные). Счёт по
графу команд, с условными переходами и с учётом подмены `a0` после
порождения, даёт 34 и 372; подвидовые числа ниже от этого не изменились.

| жизни | видов | | неуязвимость | видов | | маска | видов |
|---|---|---|---|---|---|---|---|
| 1 | 6 | | 10 кадров | 12 | | `$FFFF` | 19 |
| 8 | 4 | | 48 | 4 | | `$00FF` | 1 |
| 3 | 1 | | 20 | 2 | | `$0400` | 1 |
| 2 | 1 | | 15 | 2 | | `$0000` | 1 |
| не ставят | 10 | | 16 и 30 | по 1 | | | |

Две крайности стоит назвать отдельно:

* `$2A17D8` (код 161, 15 клеток) идёт с маской `$0000` — **не берёт вообще
  ничего**, неуязвим по построению;
* `$29F1DA` (код 136) с маской `$0400` и `$29B95C` (код 148) с `$00FF` —
  берут только часть типов урона.

### Что означают биты маски

Тип удара кладут в `+$44` жертвы, и кладут двумя способами.

**Бит 0 — постоянный тип.** Его ставят шесть мест простым
`ori.w #$0001,$44(a1)`.

**Биты 8…14 — по состоянию бьющего.** Считаются сдвигом:

```asm
	add.b	$43(a0),d0     ; урон из +$43 бьющего
	move.b	d0,$42(a1)     ; -> жертве в накопленный удар
	moveq	#1,d0
	move.b	$5(a0),d1      ; состояние бьющего
	addq.w	#8,d1
	lsl.w	d1,d0          ; 1 << (состояние + 8)
	or.w	d0,$44(a1)     ; -> жертве в тип удара
```

Байт `+$5` принимает значения 0…6 (по всем записям в него), так что биты
ложатся в 8…14. Биты 1…7 и 15 не ставит никто.

Отсюда читаются все четыре маски, которые встречаются у видов:

| маска | что принимает |
|---|---|
| `$FFFF` | всё |
| `$00FF` | только постоянный тип, бит 0 — то есть НИ ОДИН удар по состоянию |
| `$0400` | только бит 10, то есть удар при состоянии бьющего 2 |
| `$0000` | ничего, неуязвим |

Самые заметные:

| клеток | код | конструктор | обновление | жизни | неуязв. | маска | кадр |
|---|---|---|---|---|---|---|---|
| 82 | 160 | `$2A2E04` | `$2A2E3E` | — | 16 | `$FFFF` | 2202 |
| 41 | 169 | `$2A0DC4` | `$2AAAA0` | 1 | 48 | `$FFFF` | 651 |
| 28 | 148 | `$29B95C` | `$2A9FF0` | 8 | 10 | `$00FF` | 329 |
| 28 | 143 | `$2A2290` | `$2A22E0` | 1 | 30 | `$FFFF` | 2127 |
| 22 | 206 | `$29DFC4` | `$2A9A16` | — | 10 | `$FFFF` | 2647 |
| 19 | 192 | `$29F47A` | `$29F4BC` | — | 10 | `$FFFF` | 1858 |

### Жизни по умолчанию — ноль

Те десять видов, у которых конструктор не ставит `+$1C`, не «бессмертные» и
не «особенные»: общий инициализатор `loc_2996C2` кладёт туда ноль вместе с
остальными полями (`move.w d5,$1C(a0)` при `d5 = 0`). А в `loc_2A2C48`
вычитание `sub.w d1,$1C(a0)` из нуля даёт отрицательное, то есть
**смерть с первого же принятого удара**.

Сходится с уроном: `+$43` бьющего принимает значения 1, 2, 4, 5, `$0A`,
`$10`, `$25`, чаще всего 4 и 2. Жизни у тех, кто их ставит, идут от 1 до
`$5A` (90) — верхние значения у боссов. (Таблица выше построена по первым
командам конструктора и показывает только нижнюю часть этого диапазона.)

### Что делает общий конструктор

`loc_29974C` перед тем, как звать инициализатор, **гасит байт порождения в
клетке**:

```asm
	movea.l	($FFFFE140).w,a3
	clr.b	($3,a3,d3.w)       ; клетка больше не породит
```

Это парная операция к возврату номера в уборке — цикл замыкается с двух
сторон, а не только через `$FF1004`.

`loc_2996C2` раскладывает остальное, и попутно называет несколько полей:

| поле | чем инициализируется |
|---|---|
| `+$29` | номер порождения |
| `+$2A` | номер клетки |
| `+$2C`/`+$2E` | координаты клетки: положение, сдвинутое на 4 — **клетка 16 точек** |
| `+$26` | 5, длительность кадра по умолчанию |
| `+$43` | `$10`, урон по умолчанию |
| `+$1C`, `+$5`, `+$A`, `+$42`, `+$44` и прочие | ноль |

### Четвёрка в `$FF1004` — это варианты одного вида

Догадка подтвердилась: флаг ставится на **первый байт четвёрки**, а младшие
два бита номера выбирают вариант:

```asm
	moveq	#-4,d0
	and.w	d4,d0
	tst.b	($0,a1,d0.w)       ; занята ли четвёрка
	bne.s	loc_29F8B8
	addq.b	#1,($0,a1,d0.w)    ; занять
	move.w	d4,d0
	andi.w	#$0003,d0          ; а это НОМЕР ВАРИАНТА
```

Поэтому у жука коды 23, 24 и 25 идут подряд и живым бывает один.

### `$FF1104` — что объект помнит между смертями

Сразу за `$FF1004` лежит второй массив, **512 байт**, и чистится он там же
(`$298662`, 128 длинных слов). Индексируется тем же номером порождения, но
с шагом 2:

```asm
	moveq	#0,d0
	lea	($FF1104).l,a1
	move.b	$29(a0),d0     ; номер порождения
	add.w	d0,d0          ; шаг 2 -> массив слов, 256 записей
	tst.w	($0,a1,d0.w)
	beq.s	loc_2A465C
	bset	#14,$30(a0)
	move.l	#$001D8962,$22(a0)   ; ДРУГОЙ скрипт анимации
```

Это **память о том, что с этим объектом уже случилось**, и она переживает
его уничтожение. Пустая запись — объект появляется обычным; непустая — он
возвращается уже изменённым: другой скрипт, взведённый бит 14 в `+$30`, а
в одном месте (`$29C976`) значение кладут прямо в байт состояния:

```asm
	move.b	($0,a3,d0.w),$4(a0)
```

Пишут в массив шестнадцать мест: единицу (шесть раз словом, три байтом),
двойку один раз, и дважды гасят через `clr.b`. Ширина доступа смешанная —
читают словом, пишут то словом, то байтом; на поведение это не влияет,
потому что проверяют на ноль.

Вместе с `$FF1004` получается два разных учёта на один номер порождения:

| массив | ширина | что помнит |
|---|---|---|
| `$FF1004` | байт | занят ли сейчас — чтобы не породить дважды |
| `$FF1104` | слово | что с ним уже произошло — чтобы вернулся изменённым |

## Больше половины объектов вообще не думает

Если разобрать процедуры обновления всех 1945 порождённых клеток:

| | клеток | доля |
|---|---|---|
| процедура — сразу `rts` (`$2A4A7A`) | 1092 | 56% |
| настоящая логика | 827 | 43% |
| `+$1E` не ставится вовсе | 26 | 1% |

То есть **больше половины «объектов» на картах — это декорации и
неподвижные опасности**: они проигрывают свою анимацию, бьют по касанию и
ничего не решают. Различных процедур обновления всего 90 на 182
конструктора.

## Логика: три устройства

Процедур обновления 90 на 182 конструктора, но у противников они собраны
из немногих общих частей. По 372 клеткам (пересчитано `tools/enemies.py`
после того, как из счёта убрали генераторов):

| чем пользуется | клеток | доля |
|---|---|---|
| общая процедура смерти `loc_299CF8` | 295 | 79 % |
| программа поведения `+$48` | 209 | 56 % |
| автомат по таблице состояний | 197 | 53 % |
| читает указатель на игрока `$FF220C` | 82 | 22 % |
| проверка перед уроном `loc_29AA6A` | 55 | 15 % |

### Преследователь: `$2A2E3E`, 82 клетки

Самый частый вид. Раз в восемь кадров берёт игрока и правит свою скорость
так, чтобы идти к точке в 41 точке ПЕРЕД ним:

```asm
	subq.w	#1,$6(a0)
	bpl.s	loc_2A2EB4
	move.w	#$0007,$6(a0)      ; раз в 8 кадров
	movea.w	($FF220C).l,a1     ; объект игрока
	moveq	#6,d1
	add.w	$14(a1),d1         ; его Y плюс 6
	moveq	#-41,d0
	btst	#11,(a0)           ; куда сам смотрит
	beq.s	loc_2A2E8E
	neg.w	d0                 ; ...туда и смещение
loc_2A2E8E:
	add.w	$12(a1),d0         ; его X плюс-минус 41
	movem.w	$12(a0),d2/d3      ; своё место
	jsr	(loc_2A7C4E).l     ; -> направление в d4/d5
	...
	asl.w	#6,d4
	asl.w	#6,d5
	movem.w	d4/d5,$16(a0)      ; прямо в скорость
```

`$FF220C` — **указатель на объект игрока**, пишут его в одном месте
(`move.w a0,($FF220C).l`). Целятся не в самого игрока, а перед ним: `-41`
по горизонтали и `+6` по вертикали.

### Автомат: `$2AAAA0`, 41 клетка

Урон, потом переход по состоянию. Состояние — байт `+$4`, таблица та самая,
что разобрана в [open-questions.md](open-questions.md):

```asm
	moveq	#0,d0
	lea	($1FF6EA).l,a1
	move.b	$4(a0),d0
	add.w	d0,d0
	add.w	d0,d0
	movea.l	($0,a1,d0.w),a1
	jsr	(a1)
```

Таблицы состояний, которыми рулят противники, — это **те самые срезы
общего массива `$1FF646`-`$1FF746`** плюс отдельные `$1FF7AA`, `$1FF7F8`,
`$1FF47C`:

| таблица | клеток | | таблица | клеток |
|---|---|---|---|---|
| `$1FF6EA` | 52 | | `$1FF7F8` | 15 |
| `$1FF70A` | 30 | | `$1FF7AA` | 11 |
| `$1FF67A` | 28 | | `$1FF624` | 9 |
| `$1FF6FA` | 28 | | `$1FF732` | 5 |
| `$1FF646` | 23 | | `$1FF47C` | 1 |

Этот же вид, единственный из трёх, играет звук не только на смерти: при
попадании, которое не убило, идёт `$32`, при смерти `$78`.

#### Сколько состояний у автоматов

Длина таблицы — расстояние до следующего среза, но это только верхний
предел: у `$1FF624` годных указателей четыре, а запас до соседа восемь, и
дальше идёт мусор. По годности указателя получается так:

| таблица | состояний | | таблица | состояний |
|---|---|---|---|---|
| `$1FF624` | 4 (из 8 возможных) | | `$1FF6EA` | 4 |
| `$1FF646` | 7 | | `$1FF6FA` | 4 |
| `$1FF662` | 6 | | `$1FF70A` | 4 |
| `$1FF67A` | 14 | | `$1FF71A` | 6 |
| `$1FF6B2` | 14 | | `$1FF732` | 5 |

**Всего 68 состояний, а различных обработчиков 50**: пятнадцать поделены
между таблицами. Сотен записей, которых я опасался, тут нет.

#### Общий словарь состояний

Номера состояний значат одно и то же у разных видов. Это видно по тому,
что один и тот же обработчик стоит под одним и тем же номером в разных
таблицах:

* **состояние 3 — «ничего не делать»**: `$2AA678` (тело — сразу `rts`)
  стоит третьим сразу в пяти таблицах;
* состояние 0 у нескольких видов тоже пустое (`$2A98F8`, `$2A9A82`,
  `$2AA8F0` — все `rts`);
* состояние 1 — рабочее: именно единицу кладут в `+$4` чаще всего (93 раза
  против 50 у двойки и 29 у тройки).

#### Два вида — почти близнецы

`$1FF67A` и `$1FF6B2` совпадают **в 11 состояниях из 14** и расходятся
только в трёх:

| состояние | `$1FF67A` | `$1FF6B2` |
|---|---|---|
| 0 | `$2A9BC0` | `$2A9BDE` |
| 1 | `$2A9BEA` | `$2A9C34` |
| 4 | `$2A9C78` | `$2A9CAC` |

Остальные десять состояний — буквально одни и те же процедуры. То есть это
один вид с двумя вариантами поведения на входе и в движении.

#### Общий набор приёмов

Прочтение всех пятидесяти обработчиков даёт не пятьдесят разных поведений,
а десяток приёмов, из которых они сложены:

| процедура | что делает |
|---|---|
| `loc_2AB40A` | расстояние до игрока: `d0` знаковое, `d1` модуль |
| `loc_2AB41A` | то же по другой оси |
| `loc_2AB4B8` | шаг патрулирования (`d0` предел, `d6` скорость) |
| `loc_2AB4FC` | щуп края и стены (`d6` вылет, `d3` меньше нуля — упёрлись) |
| `loc_2AB514` | щуп земли и столкновения |
| `loc_2919A2` | есть ли земля в точке |
| `loc_29A982` | шаг движения |
| `loc_2AB380` | запустить цепочку обработчиков |
| `$FFFFE1DC` | X игрока, читается напрямую |

И три оборота, которые повторяются почти у всех:

```asm
	moveq	#16,d6
	bsr.w	loc_2AB4FC     ; щуп впереди
	tst.w	d3
	bpl.s	...
	bchg	#11,(a0)       ; упёрлись — РАЗВЕРНУТЬСЯ
```

```asm
	bsr.w	loc_2AB40A
	cmpi.w	#$0080,d1      ; игрок ближе 128?
	bgt.s	...
	move.b	#$01,$5(a0)    ; ЗАМЕТИЛ
```

```asm
	cmpi.b	#$02,$5(a0)    ; подсостояние 2 —
	bne.s	...
	clr.b	$5(a0)
	lea	($1FF77C).l,a1
	jsr	(loc_2AB380).l ; ...ЗАПУСТИТЬ ЦЕПОЧКУ
```

Последний оборот связывает противников с цепочками обработчиков,
разобранными в [open-questions.md](open-questions.md): подсостояние `+$5`
равное двум — это и есть сигнал «сработало, запускай цепочку».

Попутно называются поля записи: `+$8` — фаза движения по пути, `+$4C` —
цель рывка по горизонтали, `+$4E` — счётчик событий (значения 1 и 2),
`+$50`/`+$52` — пределы патрулирования или начало пути.

#### Два вида целиком

**`$1FF624` — летун по заданному пути, который стреляет.** Состояние 0
ведёт его по **синусу и косинусу**: `$1EAD94` это синус, `$1EAF94` —
он же со сдвигом на четверть оборота (см. [objects.md](objects.md)). Фаза
лежит в `+$8`, растёт на 18 за кадр и заворачивается на `$800`, значения
масштабируются сдвигами и прибавляются к центру `+$50`/`+$52`. То есть он
не «идёт по пути», а **кружит вокруг точки**.
Состояние 1 по подсостоянию 1 уходит в 2, а там выстрел: объект со
скриптом `$1D8FA6`, обработчиком `$2A97C4`, скоростью `$200` и уроном
`$10`, под звук `$82`.

**`$1FF67A` и `$1FF6B2` — крупный противник с тремя приёмами.** Состояния
читаются парами:

| состояния | что это |
|---|---|
| 7 -> 8 | **прыжок**: скорость `$0580F880`, потом посадка на высоту `$180` |
| 9 -> 10 | **рывок первый**: цель в радиусе 64, звук `$9F`, бит 14 в `+$30`, по прибытии программа порождения `$1FEFDC` |
| 11 -> 12 | **рывок второй**: то же, но звук `$5C` и программа `$1FF070` |
| 6 | щуп пола позади (`loc_2A9F56`), при находке в состояние 4 |
| 13 | **бросок по заявке скрипта**: ждёт `+$4E = 1` и зовёт `loc_2A9EAA` |

Состояния 10 и 12 устроены одинаково: двигаться, пока до цели `+$4C` не
останется шесть точек, затем сбросить признак и поставить свою программу
порождения. То есть это один и тот же рывок с разным звуком и разным
последствием.

#### Номера общих обработчиков совпадают, но словаря нет

Из 50 обработчиков пятнадцать стоят более чем в одной таблице, и **все
пятнадцать занимают в них один и тот же номер**. Ни одного исключения:

| обработчик | в скольких таблицах | под каким номером |
|---|---|---|
| `$2AA678` | 5 | всегда 3 |
| `$2AA924` | 2 | всегда 4 |
| `$2AA922` | 2 | всегда 2 |
| `$2AA8F0` | 2 | всегда 0 |
| `$2A9DE2`, `$2A9E14`, `$2A9E4A`, `$2A9E76` | по 2 | 10, 11, 12, 13 |

Но **общим словарём это назвать нельзя**, и вот опровержение: приземление
у `$1FF662` лежит под номером 3 (`$2A9AF0`), а у `$1FF71A` и `$1FF732` —
под номером 4 (`$2AA924`). Код разный, поведение одно. Совпадают номера
именно у ОБЩИХ обработчиков, то есть когда таблицы ссылаются на одну и ту
же процедуру; одинаковое поведение, переписанное дважды, спокойно садится
на разные номера.

Раньше в этом разборе я написал, что номер значит одно и то же у всех
видов. Это верно для пятнадцати общих обработчиков и неверно вообще.

#### Что удалось назвать

| номер | что это |
|---|---|
| 0, 2, 3 | бездействие: тела `$2AA8F0`, `$2AA922`, `$2AA678` — сразу `rts` |
| 1 | рабочее состояние: единицу кладут в `+$4` чаще всего, 93 раза |
| 4 | **падение и приземление** |
| 11 -> 12 | **попытка удара** с переходом при успехе |
| 6 (у `$1FF646`) | **гибель**: урон, уборка, звук `$78` |

Состояние 4, `$2AA924`, целиком:

```asm
	tst.w	$18(a0)          ; скорость по вертикали
	bmi.s	loc_2AA950       ; летим вверх — не наше
	movem.w	$12(a0),d0/d1
	addi.w	#$0010,d1        ; смотрим на 16 точек ниже
	jsr	(loc_2919A2).l   ; есть ли там земля
	beq.s	loc_2AA950
	subi.w	#$0010,d3
	move.w	d3,$14(a0)       ; встать на неё
	clr.w	$18(a0)          ; падение кончилось
	move.b	#$01,$5(a0)
```

Состояние 11, `$2A9E14`, пробует что-то в радиусе 64 и при успехе уходит в
12 со звуком `$5C`:

```asm
	moveq	#64,d2
	bsr.w	loc_2A9FA6
	tst.w	d0
	bne.s	loc_2A9E48
	move.w	d2,$4C(a0)
	move.b	#$0C,$4(a0)      ; -> состояние 12
	clr.b	$5(a0)
	...  SoundStart($5C)
```

#### Переходы, которые видно

Разметка механическая и **даёт нижнюю границу**: обход идёт до первого
`rts`, а большинство обработчиков начинается с условного выхода, так что
часть переходов остаётся за кадром. Что видно:

* `$1FF67A`: `5 -> 4`, `6 -> 4` (четвёрка — узел, куда возвращаются),
  `7 -> 8`, `9 -> 10` со звуком `$9F`, `11 -> 12` со звуком `$5C`;
* `$1FF624`: `1 -> 2`, а состояния 2 и 3 **порождают** новый объект со
  своим скриптом и звуком `$82`;
* `$1FF6EA`: состояние 1 порождает объект, звук `$37`;
* `$1FF70A`: состояния 1 и 2 крутят таймер со звуком `$74`.

#### Что делают состояния

По беглой разметке тел (что упоминается внутри):

| признак | состояний |
|---|---|
| правит скорость `+$16`/`+$18` | 8 |
| меняет состояние `+$4` | 5 |
| играет звук | 3 |
| пустое, сразу `rts` | 9 |
| прочее | остальные |

Разметка механическая, по упоминаниям в теле, а не разбор каждого
состояния по смыслу.

#### Четыре помощника: кто решает, можно ли

Все четыре стоят на одном основании — `loc_2A9FDE`, которое **поворачивает
противника лицом к игроку и заодно отдаёт расстояние**:

```asm
loc_2A9FDE:
	bsr.w	loc_2AB40A       ; d0 = X игрока - X свой, d1 = модуль
	bclr	#11,(a0)
	tst.w	d0
	bpl.s	loc_2A9FEE
	bset	#11,(a0)         ; игрок слева -> бит 11
```

Отсюда же и значение бита 11: **взгляд влево**. Проверяется дважды — в
`loc_2A9EAA` объект порождается на 40 точек левее при поднятом бите, и в
`loc_2AB3AE` знак относительной координаты переворачивается по нему же.

**`loc_2A9F56` — «есть ли пол за спиной».** Повернуться к игроку, затем
щупнуть землю в 72 точках по горизонтали и 16 вниз:

```asm
	bsr.w	loc_2A9FDE
	move.w	d0,d2            ; мёртвое: d2 дальше не читается
	moveq	#-72,d0
	btst	#11,(a0)
	beq.s	loc_2A9F66
	neg.w	d0               ; бит 11 поднят -> щуп ВПРАВО
loc_2A9F66:
	add.w	$12(a0),d0
	moveq	#16,d1
	add.w	$14(a0),d1
	jsr	(loc_2919A2).l   ; ne — земля есть
```

Знаки стоит прочитать внимательно: бит 11 поднят, когда игрок слева, а щуп
при этом уходит вправо. То есть проверяется пол **позади**, не впереди.
Вызывающий (состояние 6) при находке уходит в состояние 4.

**`loc_2A9F78` — «стоит ли прыгать».** Ноль значит «прыгай», единица —
«нет, крути программу дальше». Отказ выдаётся в трёх случаях: игрок ближе
`$80`; сам стоишь в полосе `$A0` вокруг `X = $140`; знаки `игрок - я` и
`я - $140` совпадают. Последнее условие и есть смысл всей процедуры:
совпадение знаков означает, что прыжок унесёт **от середины к стене**, и
тогда его не делают. Прыгают только назад, к середине.

**`loc_2A9FA6` — «влезет ли рывок».** В `d2` приходит запас (везде 64),
процедура кладёт цель на `d2` точек **за игроком** и проверяет её по
границам камеры:

```asm
	add.w	($FFFFE1DC).w,d2 ; цель = X игрока +- запас
	move.l	($FF1A8C).l,d3   ; сразу оба предела
	subi.w	#$0010,d3
	cmp.w	d3,d2
	bge.s	loc_2A9FDA       ; правее правого - 16 -> отказ
	swap	d3
	addi.w	#$0010,d3
	cmp.w	d3,d2
	ble.s	loc_2A9FDA       ; левее левого + 16 -> отказ
	move.b	#$01,$5(a0)      ; иначе разрешить и двинуть программу
	moveq	#0,d0
```

`$FF1A8C` и `$FF1A8E` — это **пара пределов камеры**, тех самых, по которым
её зажимает `$297780`. Для этого боя они ставятся одной командой:

```asm
	move.l	#$00200230,($FF1A8C).l   ; $29E5D6
```

То есть комната от `$20` до `$230`, и рывок разрешён, только если точка
приземления лежит хотя бы на 16 точек внутри неё. Противник заперт в той же
коробке, что и камера, — отдельных «границ арены» в записи объекта нет.

#### `+$4E` — это заявка от скрипта анимации

Счётчик читают три состояния, и все три — по одному образцу «сравнить,
обнулить, сделать»:

```asm
loc_2A9E76:                      ; состояние 13
	cmpi.w	#$0002,$4E(a0)
	bne.s	loc_2A9E98
	clr.w	$4E(a0)
	bsr.w	loc_2A9FDE
	move.w	$50(a0),d2
	lsr.w	#1,d2
	cmp.w	d2,d1            ; игрок ближе половины +$50?
	bgt.s	loc_2A9E98
	move.b	#$01,$5(a0)
loc_2A9E98:
	cmpi.w	#$0001,$4E(a0)
	bne.s	loc_2A9EA8
	clr.w	$4E(a0)
	bsr.w	loc_2A9EAA       ; бросок
```

**Во всём ПЗУ нет ни одной команды процессора, которая записала бы сюда
единицу или двойку.** Проверено полностью: 115 обращений к `+$4E` в
разобранном коде плюс побайтовый просмотр всех 130 неразобранных кусков
внутри банка `$28D000`-`$2AC000` (10 600 байт) — записи только у других
видов, которые держат в этом слове своё.

Пишет сюда **скрипт анимации**, командой `$DC`:

```
$1D8404  DC 4E 00 00    +$4E = 0        <- скрипт состояния 13
$1D8408  D8 05          держать кадр 5
$1D840A  07 24          кадр 329
$1D840C  E1 26 00 03    +$26 = 3
$1D8412  07 28          кадр 330
$1D8414  07 84          кадр 353
$1D8416  DC 4E 00 01    +$4E = 1        <- ВОТ ЗДЕСЬ бросок
$1D841A  D8 08          держать кадр 8
...
$1D842E  E1 05 00 01    +$5 = 1         <- и программа идёт дальше
```

Отсюда и всё устройство: **кадр анимации назначает момент удара**. Состояние
не считает время само, оно каждый кадр смотрит, не оставил ли скрипт заявку,
и выполняет её ровно на том кадре, где художник её поставил. Поэтому в коде
и нет записи — её там быть не должно.

Второй пример, скрипт прыжка `$1D835A`, показывает и повтор:

```
$1D8368  DC 4C 00 02    +$4C = 2          счётчик бросков
$1D837C  DC 4E 00 01    +$4E = 1          бросок
$1D8380  DE 4C FF FF    +$4C += -1
$1D8384  E5 4D FF E6    если младший байт +$4C не ноль — назад
```

`+$4D` здесь — младший байт слова `+$4C`, то есть цикл считает по тому же
слову, куда рывок кладёт цель. Поля переиспользуются между состояниями.

Всего по окну скриптов `$1D6000`-`$1DC000` команд `DC 4E` двадцать шесть.
Скрипты крупного противника — это гроздь `$1D80F4`-`$1D8446` (собрана по
всем командам `$84` его четырёх программ: `$1FEEEC` при рождении, дальше
`$1FEF54`, `$1FEFDC`, `$1FF070`), и внутри неё заявок три: `$1D8404` кладёт
ноль, `$1D8416` и `$1D837C` — единицу. **Двойки нет ни одной.** Двойку
ставят `$1D75FA` и лесенка `$1D79C8`-`$1D7A4C`, лежащие далеко за гроздью.

`loc_2A9E76` стоит в двух таблицах, но обе — этот же вид, второго
владельца у неё нет. Значит, ветка «двойка» в игре не срабатывает никогда:
единственное, что состояние 13 делает на деле, — ждёт заявку `1` и бросает.
Оговорка одна: гроздь собрана линейным проходом по программам, переходы
`$85` не исполнялись, так что это верхняя оценка набора скриптов, а не
точная достижимость.

### С проверкой: `$2A9FF0`, 28 клеток

Перед тем как считать урон, зовёт `loc_29AA6A` и, если та вернула
ненулевое, снимает бит 13 в `(a0)` и уходит другой веткой. Урон берёт
только оставшись в кадре (жизней 8, маска `$00FF`).

#### `loc_29AA6A` — проверка «я в кадре?»

Числа в ней не оставляют вариантов: `$00E0` это 224, `$0140` это 320 —
размеры экрана Mega Drive.

```asm
loc_29AA6A:                      ; d7 = поля допуска, упакованы в длинное
	move.l	d7,d6
	moveq	#0,d7
	move.l	$12(a0),d0       ; своё место, x в старшем слове, y в младшем
	move.w	($FFFFE1BE).w,d1 ; прокрутка по вертикали
	sub.w	d1,d0
	neg.w	d6
	cmp.w	d6,d0
	ble.s	loc_29AAA6       ; выше кадра больше, чем на допуск
	subi.w	#$00E0,d0        ; минус высота экрана
	neg.w	d6
	cmp.w	d6,d0
	bge.s	loc_29AAA6       ; ниже кадра
	move.w	($FFFFE1BC).w,d1 ; прокрутка по горизонтали
	swap	d0               ; теперь смотрим x
	swap	d6               ; и его допуск
	sub.w	d1,d0
	...
	subi.w	#$0140,d0        ; минус ширина экрана
	...
loc_29AAA6:
	addq.w	#1,d7            ; хоть одна граница нарушена
loc_29AAA8:
	rts
```

Возврат: **`d7` равно нулю, если объект в кадре**, и не ноль, если вышел за
любую из четырёх границ. Заодно это называет две ячейки прокрутки:
`$FFFFE1BC` по горизонтали, `$FFFFE1BE` по вертикали.

Поле допуска у каждого вызывающего своё, упаковано в длинное слово: старшее
слово — горизонтальный допуск, младшее — вертикальный. Вызовов шестнадцать:

| по горизонтали | по вертикали | раз |
|---|---|---|
| 256 | 128 | 4 |
| 128 | 256 | 2 |
| 128 | 128 | 2 |
| 4096 | 128 | 1 |
| 1280 | 128 | 1 |
| 512 | 512 | 1 |
| прочие | | по 1 |

Крайности говорят сами за себя: `4096` по горизонтали — это больше любого
уровня, то есть «считать в кадре всегда», а `128` на `128` — узкая рамка
вокруг экрана.

## Уход с экрана: две версии одной уборки

Вышедший из кадра объект не прячется, а **разбирается целиком**, и клетка,
которая его породила, получает свой номер обратно — потому противники и
появляются снова, когда возвращаешься.

Процедур таких **две**, они лежат в 112 байтах друг от друга и делают почти
одно и то же:

| | `ObjectReleaseCell` `$2918BA` | `loc_29192A` |
|---|---|---|
| команд | 35 | 17 |
| защита от повторной уборки (бит 13) | да | да |
| вернуть номер в свойства клетки | да | да |
| проверить, не видна ли клетка | **да** | нет |
| погасить байт в `$FF1004` | **да** | нет |
| отдать место в VRAM, освободить слот | да | да |

Общая часть:

```asm
	btst	#13,(a0)
	bne.s	...                    ; уже убран — выходим
	movea.l	($FFFFE140).w,a3       ; распакованные свойства клеток
	move.w	$2A(a0),d0             ; своя клетка
	move.b	$29(a0),($3,a3,d0.w)   ; номер порождения обратно в байт +3
	movem.w	$34(a0),d0/d1
	clr.l	$34(a0)
	bsr.w	loc_290E1E             ; отдать место в VRAM
	clr.w	(a0)                   ; обнулить флаги = освободить слот
```

Что клетка помнится в `+$2A`, а номер возвращается на место, уже записано в
докстринге `props()` в [tools/levels.py](../../tools/levels.py). Здесь к
этому добавляется остальное.

### Зачем их две

Проверки в них разные не по строгости, а **по смыслу, и в разных единицах**:

* `loc_29AA6A`, которую зовут снаружи, спрашивает «виден ли Я» — по
  положению `+$12`/`+$14` в точках против прокрутки `$FFFFE1BC`/`$FFFFE1BE`
  и экрана 320x224;
* проверка внутри `ObjectReleaseCell` спрашивает «видна ли МОЯ КЛЕТКА» — по
  координатам клетки `+$2C`/`+$2E` против окна `$FFFFE130`/`$FFFFE132`
  размером 28 на 16 клеток.

Это не одно и то же: объект может уйти от своей клетки далеко. Вернуть
номер, пока клетка на экране, значило бы немедленно породить дубликат.

Отсюда разделение обязанностей:

* **`loc_29192A`** — «убирай сейчас», решение уже принял вызывающий;
* **`ObjectReleaseCell`** — «убери, если моя клетка уехала», решение принимает
  сама. Её можно звать хоть каждый кадр: при клетке внутри окна она уходит
  на тот же выход, что и по биту 13, то есть **не делает ничего** — ни
  возврата номера, ни освобождения VRAM, ни слота.

Но настоящий различитель виден не в самих процедурах, а **в том, как их
зовут**. Обе начинаются с `btst #13,(a0); bne -> выход`, то есть
взведённый бит 13 запрещает уборку. И вот как это используют:

| | снимают бит 13 прямо перед вызовом |
|---|---|
| `loc_29192A` | **13 из 14** |
| `ObjectReleaseCell` | 5 из 11 |

У `loc_29192A` `bclr #13,(a0)` стоит вплотную к вызову почти всегда —
проверено с окном в две строки, цифра не меняется. То есть её вызывающие
**сами снимают запрет**, и уборка неизбежна.

`ObjectReleaseCell` зовут с запретом на месте в шести случаях из
одиннадцати — и тогда объект с взведённым битом 13 уборку просто не
проходит.

Так что это не две версии «на выбор», а **два способа употребления одной
защиты**: «сломать замок и убрать» против «постучать и уйти, если закрыто».
Раньше я описывал разницу как «кто принимает решение» — направление верное,
но различает их не это, а приставка `bclr` перед вызовом.

### Убитого не возвращают

Кто именно возродится, решает не уборка, а смерть. `loc_299CF8` первым делом
стирает привязку:

```asm
loc_299CF8:
	move.b	#$00,$29(a0)   ; забыть номер порождения
	clr.w	$2A(a0)        ; забыть свою клетку
```

А обе уборки проверяют `+$2A` и при нуле возврат пропускают. То есть
**ушедший за край возвращается, убитый — нет**, и различает их одна
очищенная ячейка.

**Осторожная версия не возвращает номер, пока клетка на экране.** Иначе
объект возродился бы на глазах у игрока:

```asm
	move.w	$2C(a0),d2
	move.w	($FFFFE130).w,d3
	cmp.w	d3,d2
	blt.s	loc_2918F8             ; левее окна — можно возвращать
	addi.w	#$001C,d3              ; окно 28 клеток по горизонтали
	cmp.w	d3,d2
	bge.s	loc_2918F8
	move.w	$2E(a0),d2
	move.w	($FFFFE132).w,d3
	...
	addi.w	#$0010,d3              ; и 16 по вертикали
	ble.s	loc_291924             ; клетка видна — НЕ возвращать
```

То есть `+$2C`/`+$2E` — координаты клетки объекта, а `$FFFFE130`/`$FFFFE132`
— начало видимого окна клеток, 28 на 16.

### `$FF1004` — «этот уже порождён»

Массив на **256 байт**, по байту на номер порождения. Чистится при входе в
уровень (`$29864C`: 64 длинных слова), и дальше живёт так:

```asm
loc_29BB02:
	move.b	d4,d5
	move.w	d5,d4              ; точный номер
	andi.w	#$FFFC,d5          ; и он же, округлённый вниз до четвёрки
	lea	($FF1004).l,a1
	tst.l	($0,a1,d5.w)       ; занят ли кто-то из ЧЕТВЁРКИ
	bne.s	loc_29BB64         ; занят — не порождаем
	bsr.w	loc_29974C         ; завести объект
	cmpa.w	#$0000,a0
	beq.w	loc_29BB64
	move.b	#$01,($0,a1,d4.w)  ; отметить СВОЙ номер занятым
```

Проверка идёт длинным словом по четвёрке, а отметка — точным байтом.
`ObjectReleaseCell` этот байт и гасит, беря номер из `+$29`.

Вместе получается замкнутый цикл:

| событие | что происходит |
|---|---|
| клетка въехала | если четвёрка свободна — объект создаётся, его байт в `$FF1004` ставится |
| объект уехал за край | номер возвращается в клетку, байт в `$FF1004` гаснет — появится снова |
| объект убит | `loc_299CF8` стирает `+$29` и `+$2A`, возвращать нечего — больше не появится |

(Соседний адрес обманчив: `$FF1004` служит ещё и верхней границей в
`GfxSetAlloc`, где от `$FF0CE4` идут четыре слота по 200 байт. Это другая
структура, размер записи объекта из неё не следует.)

## Что осталось

* Скрипт `$1D835A` считает броски через младший байт `+$4C`, а рывок кладёт
  в то же слово координату цели. Оба состояния этим словом пользуются, но
  порядок, в котором они друг другу не мешают, не проверен.
* Двадцать шесть заявок `DC 4E` по скриптам: у крупного противника разобраны
  три, остальные двадцать три принадлежат видам, которые здесь не читались.
  Лесенка `$1D79C8`-`$1D7A4C` выставляет подряд значения 0..9 — это явно
  какой-то перебор позиций, и чей он, неизвестно.
