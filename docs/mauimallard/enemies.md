# Противники: откуда берутся, чем описаны, как думают

Короткий ответ на «где противники»: **они не лежат отдельным списком**.
Противник — такой же объект, как бочка или платформа, и порождается из
клетки карты. Отличает его только то, что его процедура обновления зовёт
систему урона.

## Откуда берутся

Цепочка та же, что у всех объектов:

```
байт свойств клетки  ->  таблица `+$20` записи уровня  ->  конструктор
                                                              |
                      +$1E процедура обновления  <------------+
                      +$22 скрипт анимации       <------------+
```

По всем 23 уровням клетки порождают **1945 объектов, 182 различных
конструктора, 81 различный первый кадр**.

## Описания как такового нет

Таблицы «вид противника -> жизни, урон, скорость» в игре не существует.
Описание противника — это **сам конструктор**, и параметры в нём стоят
непосредственными операндами. Вот три варианта жука, целиком:

```asm
loc_2A43E6:
	jsr	(loc_29974C).l          ; завести объект
	cmpa.w	#$0000,a0
	beq.w	loc_2A440A              ; не завёлся — выходим
	move.l	#$002A4A7A,$1E(a0)      ; процедура обновления
	move.l	#$001D8D82,$22(a0)      ; скрипт анимации
	bset	#0,$1(a0)
	rts
```

У всех трёх вариантов процедура обновления одна и та же, а скрипты разные —
то есть «виды» здесь различаются только анимацией.

## Система урона

Её ядро — `loc_2A2C48`, и зовут его почти все настоящие противники.
Параметры передаются в регистрах, а состояние лежит в записи объекта:

| поле | что |
|---|---|
| `+$A` | таймер неуязвимости, тикает вниз |
| `+$1C` | **очки жизни** |
| `+$42` | накопленный удар, байт |
| `+$44` | тип удара, слово |

```asm
loc_2A2C48:                      ; d1 = кадры неуязвимости, d2 = маска
	moveq	#0,d0
	tst.w	$A(a0)
	beq.s	loc_2A2C58
	subq.w	#1,$A(a0)        ; неуязвим — тикаем и
	clr.b	$42(a0)          ; забываем удар
loc_2A2C58:
	tst.b	$42(a0)
	beq.s	loc_2A2C7E       ; удара не было
	and.w	$44(a0),d2       ; тип удара против маски вида
	beq.s	loc_2A2C7E       ; не тот тип — не берёт
	moveq	#1,d0
	move.w	d1,$A(a0)        ; завели неуязвимость
	moveq	#0,d1
	move.b	$42(a0),d1
	clr.b	$42(a0)
	sub.w	d1,$1C(a0)       ; сняли жизни
	beq.s	loc_2A2C7C
	bpl.s	loc_2A2C7E       ; ещё жив
loc_2A2C7C:
	subq.w	#2,d0            ; d0 = -1: умер
loc_2A2C7E:
	clr.w	$44(a0)
```

Возврат в `d0`: `0` ничего не было, `1` попали, `-1` умер.

## Параметры видов

Их три, и все три — непосредственные операнды, а не запись в таблице:
жизни ставит конструктор в `+$1C`, а кадры неуязвимости и маску уязвимости
вызывающий кладёт в `d1` и `d2` прямо перед `bsr.w loc_2A2C48`.

**Противников — 43 конструктора из 182**, на них приходится 420 клеток.

| жизни | видов | | неуязвимость | видов | | маска | видов |
|---|---|---|---|---|---|---|---|
| 1 | 6 | | 10 кадров | 12 | | `$FFFF` | 19 |
| 8 | 4 | | 48 | 4 | | `$00FF` | 1 |
| 3 | 1 | | 20 | 2 | | `$0400` | 1 |
| 2 | 1 | | 15 | 2 | | `$0000` | 1 |
| не ставят | 10 | | 16 и 30 | по 1 | | | |

Две крайности стоит назвать отдельно:

* `$2A17D8` (код 161, 15 клеток) идёт с маской `$0000` — **не берёт вообще
  ничего**, неуязвим по построению;
* `$29F1DA` (код 136) с маской `$0400` и `$29B95C` (код 148) с `$00FF` —
  берут только часть типов урона.

### Что означают биты маски

Тип удара кладут в `+$44` жертвы, и кладут двумя способами.

**Бит 0 — постоянный тип.** Его ставят шесть мест простым
`ori.w #$0001,$44(a1)`.

**Биты 8…14 — по состоянию бьющего.** Считаются сдвигом:

```asm
	add.b	$43(a0),d0     ; урон из +$43 бьющего
	move.b	d0,$42(a1)     ; -> жертве в накопленный удар
	moveq	#1,d0
	move.b	$5(a0),d1      ; состояние бьющего
	addq.w	#8,d1
	lsl.w	d1,d0          ; 1 << (состояние + 8)
	or.w	d0,$44(a1)     ; -> жертве в тип удара
```

Байт `+$5` принимает значения 0…6 (по всем записям в него), так что биты
ложатся в 8…14. Биты 1…7 и 15 не ставит никто.

Отсюда читаются все четыре маски, которые встречаются у видов:

| маска | что принимает |
|---|---|
| `$FFFF` | всё |
| `$00FF` | только постоянный тип, бит 0 — то есть НИ ОДИН удар по состоянию |
| `$0400` | только бит 10, то есть удар при состоянии бьющего 2 |
| `$0000` | ничего, неуязвим |

Самые заметные:

| клеток | код | конструктор | обновление | жизни | неуязв. | маска | кадр |
|---|---|---|---|---|---|---|---|
| 82 | 160 | `$2A2E04` | `$2A2E3E` | — | 16 | `$FFFF` | 2202 |
| 41 | 169 | `$2A0DC4` | `$2AAAA0` | 1 | 48 | `$FFFF` | 651 |
| 28 | 148 | `$29B95C` | `$2A9FF0` | 8 | 10 | `$00FF` | 329 |
| 28 | 143 | `$2A2290` | `$2A22E0` | 1 | 30 | `$FFFF` | 2127 |
| 22 | 206 | `$29DFC4` | `$2A9A16` | — | 10 | `$FFFF` | 2647 |
| 19 | 192 | `$29F47A` | `$29F4BC` | — | 10 | `$FFFF` | 1858 |

### Жизни по умолчанию — ноль

Те десять видов, у которых конструктор не ставит `+$1C`, не «бессмертные» и
не «особенные»: общий инициализатор `loc_2996C2` кладёт туда ноль вместе с
остальными полями (`move.w d5,$1C(a0)` при `d5 = 0`). А в `loc_2A2C48`
вычитание `sub.w d1,$1C(a0)` из нуля даёт отрицательное, то есть
**смерть с первого же принятого удара**.

Сходится с уроном: `+$43` бьющего принимает значения 1, 2, 4, 5, `$0A`,
`$10`, `$25`, чаще всего 4 и 2. Жизни у тех, кто их ставит, идут от 1 до
`$5A` (90) — верхние значения у боссов. (Таблица выше построена по первым
командам конструктора и показывает только нижнюю часть этого диапазона.)

### Что делает общий конструктор

`loc_29974C` перед тем, как звать инициализатор, **гасит байт порождения в
клетке**:

```asm
	movea.l	($FFFFE140).w,a3
	clr.b	($3,a3,d3.w)       ; клетка больше не породит
```

Это парная операция к возврату номера в уборке — цикл замыкается с двух
сторон, а не только через `$FF1004`.

`loc_2996C2` раскладывает остальное, и попутно называет несколько полей:

| поле | чем инициализируется |
|---|---|
| `+$29` | номер порождения |
| `+$2A` | номер клетки |
| `+$2C`/`+$2E` | координаты клетки: положение, сдвинутое на 4 — **клетка 16 точек** |
| `+$26` | 5, длительность кадра по умолчанию |
| `+$43` | `$10`, урон по умолчанию |
| `+$1C`, `+$5`, `+$A`, `+$42`, `+$44` и прочие | ноль |

### Четвёрка в `$FF1004` — это варианты одного вида

Догадка подтвердилась: флаг ставится на **первый байт четвёрки**, а младшие
два бита номера выбирают вариант:

```asm
	moveq	#-4,d0
	and.w	d4,d0
	tst.b	($0,a1,d0.w)       ; занята ли четвёрка
	bne.s	loc_29F8B8
	addq.b	#1,($0,a1,d0.w)    ; занять
	move.w	d4,d0
	andi.w	#$0003,d0          ; а это НОМЕР ВАРИАНТА
```

Поэтому у жука коды 23, 24 и 25 идут подряд и живым бывает один.

### `$FF1104` — что объект помнит между смертями

Сразу за `$FF1004` лежит второй массив, **512 байт**, и чистится он там же
(`$298662`, 128 длинных слов). Индексируется тем же номером порождения, но
с шагом 2:

```asm
	moveq	#0,d0
	lea	($FF1104).l,a1
	move.b	$29(a0),d0     ; номер порождения
	add.w	d0,d0          ; шаг 2 -> массив слов, 256 записей
	tst.w	($0,a1,d0.w)
	beq.s	loc_2A465C
	bset	#14,$30(a0)
	move.l	#$001D8962,$22(a0)   ; ДРУГОЙ скрипт анимации
```

Это **память о том, что с этим объектом уже случилось**, и она переживает
его уничтожение. Пустая запись — объект появляется обычным; непустая — он
возвращается уже изменённым: другой скрипт, взведённый бит 14 в `+$30`, а
в одном месте (`$29C976`) значение кладут прямо в байт состояния:

```asm
	move.b	($0,a3,d0.w),$4(a0)
```

Пишут в массив шестнадцать мест: единицу (шесть раз словом, три байтом),
двойку один раз, и дважды гасят через `clr.b`. Ширина доступа смешанная —
читают словом, пишут то словом, то байтом; на поведение это не влияет,
потому что проверяют на ноль.

Вместе с `$FF1004` получается два разных учёта на один номер порождения:

| массив | ширина | что помнит |
|---|---|---|
| `$FF1004` | байт | занят ли сейчас — чтобы не породить дважды |
| `$FF1104` | слово | что с ним уже произошло — чтобы вернулся изменённым |

## Больше половины объектов вообще не думает

Если разобрать процедуры обновления всех 1945 порождённых клеток:

| | клеток | доля |
|---|---|---|
| процедура — сразу `rts` (`$2A4A7A`) | 1092 | 56% |
| настоящая логика | 827 | 43% |
| `+$1E` не ставится вовсе | 26 | 1% |

То есть **больше половины «объектов» на картах — это декорации и
неподвижные опасности**: они проигрывают свою анимацию, бьют по касанию и
ничего не решают. Различных процедур обновления всего 90 на 182
конструктора.

## Логика: три устройства

Процедур обновления 90 на 182 конструктора, но у противников они собраны
из немногих общих частей. По 420 клеткам:

| чем пользуется | клеток | доля |
|---|---|---|
| общая процедура смерти `loc_299CF8` | 302 | 72% |
| автомат по таблице состояний | 202 | 48% |
| проверка перед уроном `loc_29AA6A` | 107 | 25% |
| читает указатель на игрока `$FF220C` | 83 | 20% |

### Преследователь: `$2A2E3E`, 82 клетки

Самый частый вид. Раз в восемь кадров берёт игрока и правит свою скорость
так, чтобы идти к точке в 41 точке ПЕРЕД ним:

```asm
	subq.w	#1,$6(a0)
	bpl.s	loc_2A2EB4
	move.w	#$0007,$6(a0)      ; раз в 8 кадров
	movea.w	($FF220C).l,a1     ; объект игрока
	moveq	#6,d1
	add.w	$14(a1),d1         ; его Y плюс 6
	moveq	#-41,d0
	btst	#11,(a0)           ; куда сам смотрит
	beq.s	loc_2A2E8E
	neg.w	d0                 ; ...туда и смещение
loc_2A2E8E:
	add.w	$12(a1),d0         ; его X плюс-минус 41
	movem.w	$12(a0),d2/d3      ; своё место
	jsr	(loc_2A7C4E).l     ; -> направление в d4/d5
	...
	asl.w	#6,d4
	asl.w	#6,d5
	movem.w	d4/d5,$16(a0)      ; прямо в скорость
```

`$FF220C` — **указатель на объект игрока**, пишут его в одном месте
(`move.w a0,($FF220C).l`). Целятся не в самого игрока, а перед ним: `-41`
по горизонтали и `+6` по вертикали.

### Автомат: `$2AAAA0`, 41 клетка

Урон, потом переход по состоянию. Состояние — байт `+$4`, таблица та самая,
что разобрана в [open-questions.md](open-questions.md):

```asm
	moveq	#0,d0
	lea	($1FF6EA).l,a1
	move.b	$4(a0),d0
	add.w	d0,d0
	add.w	d0,d0
	movea.l	($0,a1,d0.w),a1
	jsr	(a1)
```

Таблицы состояний, которыми рулят противники, — это **те самые срезы
общего массива `$1FF646`-`$1FF746`** плюс отдельные `$1FF7AA`, `$1FF7F8`,
`$1FF47C`:

| таблица | клеток | | таблица | клеток |
|---|---|---|---|---|
| `$1FF6EA` | 52 | | `$1FF7F8` | 15 |
| `$1FF70A` | 30 | | `$1FF7AA` | 11 |
| `$1FF67A` | 28 | | `$1FF624` | 9 |
| `$1FF6FA` | 28 | | `$1FF732` | 5 |
| `$1FF646` | 23 | | `$1FF47C` | 1 |

Этот же вид, единственный из трёх, играет звук не только на смерти: при
попадании, которое не убило, идёт `$32`, при смерти `$78`.

#### Сколько состояний у автоматов

Длина таблицы — расстояние до следующего среза, но это только верхний
предел: у `$1FF624` годных указателей четыре, а запас до соседа восемь, и
дальше идёт мусор. По годности указателя получается так:

| таблица | состояний | | таблица | состояний |
|---|---|---|---|---|
| `$1FF624` | 4 (из 8 возможных) | | `$1FF6EA` | 4 |
| `$1FF646` | 7 | | `$1FF6FA` | 4 |
| `$1FF662` | 6 | | `$1FF70A` | 4 |
| `$1FF67A` | 14 | | `$1FF71A` | 6 |
| `$1FF6B2` | 14 | | `$1FF732` | 5 |

**Всего 68 состояний, а различных обработчиков 50**: пятнадцать поделены
между таблицами. Сотен записей, которых я опасался, тут нет.

#### Общий словарь состояний

Номера состояний значат одно и то же у разных видов. Это видно по тому,
что один и тот же обработчик стоит под одним и тем же номером в разных
таблицах:

* **состояние 3 — «ничего не делать»**: `$2AA678` (тело — сразу `rts`)
  стоит третьим сразу в пяти таблицах;
* состояние 0 у нескольких видов тоже пустое (`$2A98F8`, `$2A9A82`,
  `$2AA8F0` — все `rts`);
* состояние 1 — рабочее: именно единицу кладут в `+$4` чаще всего (93 раза
  против 50 у двойки и 29 у тройки).

#### Два вида — почти близнецы

`$1FF67A` и `$1FF6B2` совпадают **в 11 состояниях из 14** и расходятся
только в трёх:

| состояние | `$1FF67A` | `$1FF6B2` |
|---|---|---|
| 0 | `$2A9BC0` | `$2A9BDE` |
| 1 | `$2A9BEA` | `$2A9C34` |
| 4 | `$2A9C78` | `$2A9CAC` |

Остальные десять состояний — буквально одни и те же процедуры. То есть это
один вид с двумя вариантами поведения на входе и в движении.

#### Что делают состояния

По беглой разметке тел (что упоминается внутри):

| признак | состояний |
|---|---|
| правит скорость `+$16`/`+$18` | 8 |
| меняет состояние `+$4` | 5 |
| играет звук | 3 |
| пустое, сразу `rts` | 9 |
| прочее | остальные |

Разметка механическая, по упоминаниям в теле, а не разбор каждого
состояния по смыслу.

### С проверкой: `$2A9FF0`, 28 клеток

Перед тем как считать урон, зовёт `loc_29AA6A` и, если та вернула
ненулевое, снимает бит 13 в `(a0)` и уходит другой веткой. Урон берёт
только оставшись в кадре (жизней 8, маска `$00FF`).

#### `loc_29AA6A` — проверка «я в кадре?»

Числа в ней не оставляют вариантов: `$00E0` это 224, `$0140` это 320 —
размеры экрана Mega Drive.

```asm
loc_29AA6A:                      ; d7 = поля допуска, упакованы в длинное
	move.l	d7,d6
	moveq	#0,d7
	move.l	$12(a0),d0       ; своё место, x в старшем слове, y в младшем
	move.w	($FFFFE1BE).w,d1 ; прокрутка по вертикали
	sub.w	d1,d0
	neg.w	d6
	cmp.w	d6,d0
	ble.s	loc_29AAA6       ; выше кадра больше, чем на допуск
	subi.w	#$00E0,d0        ; минус высота экрана
	neg.w	d6
	cmp.w	d6,d0
	bge.s	loc_29AAA6       ; ниже кадра
	move.w	($FFFFE1BC).w,d1 ; прокрутка по горизонтали
	swap	d0               ; теперь смотрим x
	swap	d6               ; и его допуск
	sub.w	d1,d0
	...
	subi.w	#$0140,d0        ; минус ширина экрана
	...
loc_29AAA6:
	addq.w	#1,d7            ; хоть одна граница нарушена
loc_29AAA8:
	rts
```

Возврат: **`d7` равно нулю, если объект в кадре**, и не ноль, если вышел за
любую из четырёх границ. Заодно это называет две ячейки прокрутки:
`$FFFFE1BC` по горизонтали, `$FFFFE1BE` по вертикали.

Поле допуска у каждого вызывающего своё, упаковано в длинное слово: старшее
слово — горизонтальный допуск, младшее — вертикальный. Вызовов шестнадцать:

| по горизонтали | по вертикали | раз |
|---|---|---|
| 256 | 128 | 4 |
| 128 | 256 | 2 |
| 128 | 128 | 2 |
| 4096 | 128 | 1 |
| 1280 | 128 | 1 |
| 512 | 512 | 1 |
| прочие | | по 1 |

Крайности говорят сами за себя: `4096` по горизонтали — это больше любого
уровня, то есть «считать в кадре всегда», а `128` на `128` — узкая рамка
вокруг экрана.

| `$18` | 56 |

## Уход с экрана: две версии одной уборки

Вышедший из кадра объект не прячется, а **разбирается целиком**, и клетка,
которая его породила, получает свой номер обратно — потому противники и
появляются снова, когда возвращаешься.

Процедур таких **две**, они лежат в 112 байтах друг от друга и делают почти
одно и то же:

| | `ObjectReleaseCell` `$2918BA` | `loc_29192A` |
|---|---|---|
| команд | 35 | 17 |
| защита от повторной уборки (бит 13) | да | да |
| вернуть номер в свойства клетки | да | да |
| проверить, не видна ли клетка | **да** | нет |
| погасить байт в `$FF1004` | **да** | нет |
| отдать место в VRAM, освободить слот | да | да |

Общая часть:

```asm
	btst	#13,(a0)
	bne.s	...                    ; уже убран — выходим
	movea.l	($FFFFE140).w,a3       ; распакованные свойства клеток
	move.w	$2A(a0),d0             ; своя клетка
	move.b	$29(a0),($3,a3,d0.w)   ; номер порождения обратно в байт +3
	movem.w	$34(a0),d0/d1
	clr.l	$34(a0)
	bsr.w	loc_290E1E             ; отдать место в VRAM
	clr.w	(a0)                   ; обнулить флаги = освободить слот
```

Что клетка помнится в `+$2A`, а номер возвращается на место, уже записано в
докстринге `props()` в [tools/levels.py](../../tools/levels.py). Здесь к
этому добавляется остальное.

### Зачем их две

Проверки в них разные не по строгости, а **по смыслу, и в разных единицах**:

* `loc_29AA6A`, которую зовут снаружи, спрашивает «виден ли Я» — по
  положению `+$12`/`+$14` в точках против прокрутки `$FFFFE1BC`/`$FFFFE1BE`
  и экрана 320x224;
* проверка внутри `ObjectReleaseCell` спрашивает «видна ли МОЯ КЛЕТКА» — по
  координатам клетки `+$2C`/`+$2E` против окна `$FFFFE130`/`$FFFFE132`
  размером 28 на 16 клеток.

Это не одно и то же: объект может уйти от своей клетки далеко. Вернуть
номер, пока клетка на экране, значило бы немедленно породить дубликат.

Отсюда разделение обязанностей:

* **`loc_29192A`** — «убирай сейчас», решение уже принял вызывающий;
* **`ObjectReleaseCell`** — «убери, если моя клетка уехала», решение принимает
  сама. Её можно звать хоть каждый кадр: при клетке внутри окна она уходит
  на тот же выход, что и по биту 13, то есть **не делает ничего** — ни
  возврата номера, ни освобождения VRAM, ни слота.

### Убитого не возвращают

Кто именно возродится, решает не уборка, а смерть. `loc_299CF8` первым делом
стирает привязку:

```asm
loc_299CF8:
	move.b	#$00,$29(a0)   ; забыть номер порождения
	clr.w	$2A(a0)        ; забыть свою клетку
```

А обе уборки проверяют `+$2A` и при нуле возврат пропускают. То есть
**ушедший за край возвращается, убитый — нет**, и различает их одна
очищенная ячейка.

**Осторожная версия не возвращает номер, пока клетка на экране.** Иначе
объект возродился бы на глазах у игрока:

```asm
	move.w	$2C(a0),d2
	move.w	($FFFFE130).w,d3
	cmp.w	d3,d2
	blt.s	loc_2918F8             ; левее окна — можно возвращать
	addi.w	#$001C,d3              ; окно 28 клеток по горизонтали
	cmp.w	d3,d2
	bge.s	loc_2918F8
	move.w	$2E(a0),d2
	move.w	($FFFFE132).w,d3
	...
	addi.w	#$0010,d3              ; и 16 по вертикали
	ble.s	loc_291924             ; клетка видна — НЕ возвращать
```

То есть `+$2C`/`+$2E` — координаты клетки объекта, а `$FFFFE130`/`$FFFFE132`
— начало видимого окна клеток, 28 на 16.

### `$FF1004` — «этот уже порождён»

Массив на **256 байт**, по байту на номер порождения. Чистится при входе в
уровень (`$29864C`: 64 длинных слова), и дальше живёт так:

```asm
loc_29BB02:
	move.b	d4,d5
	move.w	d5,d4              ; точный номер
	andi.w	#$FFFC,d5          ; и он же, округлённый вниз до четвёрки
	lea	($FF1004).l,a1
	tst.l	($0,a1,d5.w)       ; занят ли кто-то из ЧЕТВЁРКИ
	bne.s	loc_29BB64         ; занят — не порождаем
	bsr.w	loc_29974C         ; завести объект
	cmpa.w	#$0000,a0
	beq.w	loc_29BB64
	move.b	#$01,($0,a1,d4.w)  ; отметить СВОЙ номер занятым
```

Проверка идёт длинным словом по четвёрке, а отметка — точным байтом.
`ObjectReleaseCell` этот байт и гасит, беря номер из `+$29`.

Вместе получается замкнутый цикл:

| событие | что происходит |
|---|---|
| клетка въехала | если четвёрка свободна — объект создаётся, его байт в `$FF1004` ставится |
| объект уехал за край | номер возвращается в клетку, байт в `$FF1004` гаснет — появится снова |
| объект убит | `loc_299CF8` стирает `+$29` и `+$2A`, возвращать нечего — больше не появится |

(Соседний адрес обманчив: `$FF1004` служит ещё и верхней границей в
`GfxSetAlloc`, где от `$FF0CE4` идут четыре слота по 200 байт. Это другая
структура, размер записи объекта из неё не следует.)

## Что осталось

* **Смысл каждого отдельного состояния.** Границы таблиц, общий словарь
  номеров и механическая разметка тел — выше; чего нет, так это разбора
  каждой из 50 процедур по существу.
* **Почему выбор между двумя уборками не строгий.** Правило «кто принимает
  решение» видно из устройства, но по площадкам не выдержано: проверка
  экрана стоит рядом с `loc_29192A` в 6 случаях из 14 и рядом с осторожной
  в 3 из 11.
