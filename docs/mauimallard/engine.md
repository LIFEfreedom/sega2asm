# Движок: вход, прерывания, ядро

## Как игра стартует

| адрес | что происходит |
|---|---|
| `$2979E4` | `EntryPoint`. Проверка `$A10008`/`$A1000C` — если игра уже инициализирована, сразу на `$297ADE` |
| `$2979F4` | берётся таблица инициализации `$297A72`: `d5=$8000`, `d6=$3FFF`, `d7=$0100`, `a0=$A00000` (ОЗУ Z80), `a1=$A11100` (запрос шины), `a2=$A11200` (сброс), `a3=$C00000` (данные VDP), `a4=$C00004` (управление VDP) |
| `$297A0A` | защита TMSS: `'SEGA'` в `$A14000`, но только если в `$A10001` есть версия |
| `$297A1C` | 24 регистра VDP из той же таблицы, затем очистка VRAM, CRAM и VSRAM |
| `$297AE6` | **48 команд `nop` подряд** — задержка после инициализации VDP |
| `$297B46` | `bra.w $297F4A` — настоящее начало игры |
| `$297F4A` | `suba.l a7,a7` (стек = 0), запуск драйвера Z80, определение PAL, главный цикл |

Порядок стандартный для картриджей Sega; ничего своего в загрузке нет.

**Определение PAL.** `$297F94`: бит 0 слова состояния VDP. Если PAL —
в `$FF217E` кладётся 1 и звуку уходит команда `$1B` с аргументом 1
(вероятно, поправка темпа). Это же `$FF217E` читает обработчик кадрового
прерывания.

## Прерывания

Настоящих векторов три: сброс `$2979E4`, строчное (уровень 4) `$296976`,
кадровое (уровень 6) `$2968FE`. Остальные 61 — нули или мусор, не
попадающий даже в адресное пространство ROM.

### Кадровое, `$2968FE`

```
addq.w  #1,($FFFFE196).w        ; счётчик кадров
                                 ; при PAL ($FF217E≠0) — ожидание по $C00008
цикл 1: $FFFFE166..$FFFFE176    ; 4 слота, вызываются как есть
цикл 2: $FFFFE176..$FFFFE196    ; 8 слотов, но:
          - защита от повторного входа флагом $FF0506
          - sr = $2300, то есть прерывания РАЗРЕШЕНЫ на время вызова
```

То есть у игры два списка обработчиков кадра: короткий «жёсткий» (для
работы с VDP) и длинный «мягкий», который может занимать больше кадра и
не блокирует следующее прерывание.

### Строчное, `$296976`

Один указатель — `$FFFFE198`. По умолчанию там `$29698A`, а это `rts`.
Ставится в `$295DA6`.

## Ядро: регистрация обработчиков и ожидание кадра

| адрес | что делает |
|---|---|
| `$2967B6` | ждать смены счётчика `$FFFFE196` (ждать кадр) |
| `$2967C6` | ждать начала и конца обратного хода по биту 3 состояния VDP |
| `$2967E2` | то же, но в обратном порядке |
| `$2967FE` | добавить `a0` в **короткий** список (4 слота, `$FFFFE166`) |
| `$296822` | добавить `a0` в **длинный** список (8 слотов, `$FFFFE176`) |
| `$29684E` | добавить в длинный, если его там ещё нет |
| `$29687E` | убрать `a0` из короткого списка |
| `$2968AA` | убрать `a0` из длинного списка |
| `$2968D6` | очистить длинный список целиком |
| `$296B0C` | генератор случайных чисел; состояние — `$FFFFE14E` (32 бита) |

Списки — просто массивы длинных слов, ноль = пустой слот. Все операции
делаются под `ori.w #$0700,sr`.

## Распаковка записи уровня

`$2984C2` (его зовёт главный цикл как `LevelSetup`) раскладывает запись
уровня по ОЗУ. Сначала находит её — и тут важно, что `$1FCB50` это
**таблица указателей**, а не сами записи:

```asm
	move.w	($FF1B14).l,d1   ; номер уровня
	add.w	d1,d1
	add.w	d1,d1            ; *4, а не *$42
	lea	($1FCB50).l,a0
	movea.l	($0,a0,d1.w),a0  ; длинное слово — адрес записи
```

Дальше идёт сплошное копирование, поле за полем:

| поле | размер | куда | что известно |
|---|---|---|---|
| `+$00` | длинное | `$FF1B1A` | палитра |
| `+$04` | длинное | `$FF1B1E` | профили земли |
| `+$08` | длинное | `$FF1B16` | графика |
| `+$0C` | длинное | `$FF1A72` | **писатель горизонтальной прокрутки** ([camera.md](camera.md)) |
| `+$10` | длинное | `$FF1A76` | **писатель вертикальной прокрутки** |
| `+$14` | длинное | `$FF1A7A` | **построение фона на кадр** |
| `+$18` | длинное | `$FF1B26` | **таблица анимации тайлов** |
| `+$1C` | длинное | `$FF1A7E` + `$FF1A61` | **таблица анимации ПАЛИТРЫ**; ноль — не включать |
| `+$20` | длинное | `$FF1B32` | таблица обработчиков порождения |
| `+$24` | длинное | `$FF1B36` | вторая таблица обработчиков |
| `+$28` | длинное | `$FF1B3A` | обработчик кадра, который вешают на время уровня (`loc_2967FE`); у всех 23 один и тот же `$2A526E` |
| `+$2C` | длинное | `$FF1B3E` | **процедура уровня: ею и заводятся боссы** |
| `+$30` | длинное | `$FF1B4A` | зовут сразу после процедуры уровня и перед `PaletteFadeTo`; у всех 23 это `$298B4E` |
| `+$34` | слово | `$FF1B22` | регистр 11 VDP — режим прокрутки; ОБЯЗАН согласовываться с `+$0C` и `+$10`, сходится 23 из 23 (`tools/scroll.py --check`) |
| `+$36` | длинное | `$FF1B2A`, оттуда же в `$FFFFFD86` | **где начинать**: два слова, X и Y, идут прямо в `+$12` игрока. Копируются, только если `$FFFFFD86` пустой — то есть точка возврата побеждает |
| `+$3A` | слово | `$FF1B24` | **сколько в ней записей** |
| `+$3C` | слово | `$FF1B46` | **номер музыки уровня** |
| `+$3E` | слово | `$FF2131` (байт) | **вязкость**: при единице `$2A4E1A` отнимает от горизонтальной скорости половину. Единица стоит только у уровней 14 и 15 — тех самых, где камера качается по косинусу ([camera.md](camera.md)). Ненулевое даёт также `$0C00` вместо `$0600` в `$FF1B4E` |
| `+$40` | слово | `$FF1B48` | **после победы показать заставку**: звук, `$FF1394 = 1` (музыка) и `$FF213C = 1` (заставка); единица стоит у десяти уровней: 2, 6, 9, 11, 13, 15, 17, 18, 21, 22 |

Запись `$42` байта (шаг между записями ровно 66, проверено по всем 23), и
**покрыта она целиком** — безымянных полей не осталось.

### Поправка: анимация палитры НЕ вырезана, она играет

В первом разборе я написал, что поле `+$1C` не читает никто и заготовленная
цветовая анимация из игры исчезла. **Это неверно, и ошибка была в том, что
я не дочитал распаковщик.** Строчек через четырнадцать после копирования
`+$36` стоит:

```asm
	move.l	$1C(a0),d0
	beq.s	loc_2985BE
	move.l	d0,($FF1A7E).l       ; таблица
	move.b	#$01,($FF1A61).l     ; и разрешение
```

А `$FF1A7E` с `$FF1A61` — это ровно то, что каждый кадр читает `$2A57CA`,
которого зовут построители фона по полю `+$14`. Он ведёт по записи счётчик
в `$FF1B54`, а готовые пары кладёт в очередь `$FF1BDC`:

```asm
	move.w	$2(a1),(a3)+         ; индекс CRAM
	move.w	($6,a1,d2.w),(a3)+   ; цвет
```

Очередь разбирает `$2A574C` и пишет прямо в CRAM:

```asm
	move.w	(a0)+,d0
	bmi.s	loc_2A576C           ; $FFFF — конец
	lsl.l	#3,d0
	lsr.w	#2,d0
	ori.w	#$C000,d0            ; команда записи CRAM
	swap	d0
	move.l	d0,(a4)
	move.w	(a0)+,(a5)
```

То есть цепочка целая: **поле уровня -> `$FF1A7E` -> `$2A57CA` -> очередь
`$FF1BDC` -> CRAM**. Проигрыватель на месте, и уровни 6, 10, 11, 12 и 13
действительно мерцают.

**Заодно нашлась седьмая таблица.** Уровень 3 включает анимацию не записью,
а меткой на карте: объект `$29BFE0` кладёт в `$FF1A7E` адрес `$288A8A`, а
`$29BFFC` гасит разрешение и шлёт восстановительный кусок палитры `$288B5E`
([objects.md](objects.md)). Разбирается `$288A8A` тем же форматом без
остатка: семь записей по двенадцать цветов, индексы CRAM 17-23 подряд,
задержка 1, и цвета — бегущая волна красного `200 400 ... E00 ... 200`,
сдвинутая по фазе на шаг между соседними индексами. Конец таблицы — ровно
`$288B5E`, то есть встык с тем куском, который шлёт выключатель.

Формат записи (он же был описан верно):

```
слово  N                      число записей
на запись:
    слово  cnt                сколько цветов в цикле
    слово  idx                индекс CRAM
    слово  par                задержка
    cnt слов                  сами цвета, обычные 0BGR
```

Шаг записи `6 + 2 * cnt` — его считает сам обходчик
(`addi.w #$0006,d2` после `add.w d2,d2`).

Заодно распаковщик кладёт в `$FF1B42` постоянное `$2A6454` и гасит
`$FF216E`, `$FF1A61`, `$FF1A62`.

## Процедура уровня `+$2C`: чем заводятся боссы

Поле `+$2C` записи (в ОЗУ `$FF1B3E`) — **процедура самого уровня**, и
именно она расставляет то, чего нет на карте. У большинства уровней она
мелкая (у 8 и 9 это `clr.b ($FF213E); rts`), а у боевых — расстановка
соперника по готовым координатам:

```asm
loc_2A61A2:                      ; уровень 6
	jsr	(loc_296D16).l
	...	SoundStart($54)
	move.w	#$00F9,d1
	move.w	#$0130,d2
	bsr.w	loc_2A3CFE       ; первый
	move.l	#$002A3B04,$50(a0)
	move.w	a0,($FF214E).l
	move.w	#$0184,d1
	move.w	#$0130,d2
	bsr.w	loc_2A3CFE       ; второй, зеркально
	move.w	a0,($FF2150).l
	bset	#11,(a0)
	...	loc_29974C, $6 = $5A, $1E = $2A410C
```

Проверено по достижимости: из `$2A61A2` заводятся пять процедур обновления
с уроном — `$2AA090`, `$2AA132`, `$2AA1CC`, `$2AA266`, `$2AA3A8`, и все пять
ходят по срезу `$1FF6B2` с маской `$00FF`. То есть босс второго мира — это
**набор из пяти уток-ниндзя на том же автомате**, что и рядовой противник
с кодом 148. Из `$2A6156` (уровень 18) так же заводятся `$2A8EA4` и
`$2A93D0`.

Координаты у обоих зашиты числами: `$F9`/`$184` по горизонтали и `$130` по
вертикали у шестого, `$1F0`, `$590`, `$3C8` у восемнадцатого.

### Слот текущей фазы `$FF2214`

Многочастный босс `$2A7000`-`$2A9400` меняет поведение не состоянием, а
подменой процедуры обновления через слот:

| адрес | что |
|---|---|
| `$2A7AEE` | `$FF2214 <- $2A6FF8` |
| `$2A7B46` | `$FF2214 <- $2A71E0` |
| `$2A7B94` | `$FF2214 <- $2A7244` |
| `$2A7906` | `move.l ($FF2214).l,$1E(a0)` — забрать фазу |

Голова этого гнезда — `$2A7AAA`, и ставит её **клетка**: конструктор
`$2A0E6C` (код 202, одна клетка на уровне 10) зовёт `loc_29974C` дважды и
второму объекту кладёт `$1E = $2A7AAA`.

### Бонус вместо боя: уровни 19-22

Уровни 19-22 (`BABALUAU BABY`) — не бой, а бонусная игра, и попадают в неё
подменой номера уровня в `$2982A0`, если ненулевое `$FF1350`:

| с уровня | на уровень |
|---|---|
| 2 | 19 |
| 9 | 20 |
| 13 | 21 |
| 17 | 22 |

Номер сохраняется на стеке и возвращается назад в `$29834A`. Процедура
`+$2C` у всех четырёх одна, `$2A601C`, и она ставит **игроку** состояние
`$2C` и скрипт `$1D7732` — то есть танец, а не уровень.

## Таблицы обработчиков порождения: `$288CB2`-`$28D000`

Промежуток между концом графики уровней и началом банка кода занят не
чем-то неизвестным, а **девятью таблицами обработчиков порождения** — тем
самым полем `+$20` записи уровня. На 23 уровня их девять, то есть по одной
на мир.

Точнее — **таблиц на мир две**, и лежат они встык:

| | |
|---|---|
| первая, поле `+$20` | `$288CB2` и далее с шагом 2044 |
| вторая, поле `+$24` | ровно `первая + 1020` |
| размер каждой | 256 длинных слов: индекс БАЙТОВЫЙ |
| заглушка «ничего не делать» | `$2A526C`, три четверти всех записей |

Всего в ряду 340 различных обработчиков.

Сначала шаг 2044 выглядел как «таблица из 511 записей, и вторая половина
неизвестно чем адресуется». Разрешилось проверкой адресов: `+$24` у всех
девяти миров равно `+$20` плюс 1020, то есть это отдельное поле со своей
таблицей, а не хвост первой. Обе читают одинаково — байтом:

```asm
	moveq	#0,d0
	move.b	d4,d0
	add.w	d0,d0
	add.w	d0,d0
	movea.l	($0,a6,d0.w),a6
	jsr	(a6)
```

Байтовый индекс и объясняет размер: больше 256 записей не достать. В ОЗУ
поля уходят в `$FF1B32` (`+$20`) и `$FF1B36` (`+$24`).

## Программы поведения `+$48`: четырнадцать команд

Поле `+$48` — не адрес подпрограммы, а **указатель на байт-код**. Толкователь
`loc_2AB346` короткий, и из него язык читается целиком:

```asm
loc_2AB346:
	movea.l	$48(a0),a1           ; где стоим
	lea	(loc_2A64AE).l,a2    ; таблица из bra.w
loc_2AB350:
	moveq	#0,d0
	move.b	(a1),d0              ; ПОДСМОТРЕТЬ байт, не сдвигая
	subi.b	#$80,d0
	bcs.s	loc_2AB364           ; меньше $80 — это конец шага
	add.w	d0,d0
	add.w	d0,d0
	jsr	($0,a2,d0.w)         ; команда сама двигает a1
	bra.s	loc_2AB350
loc_2AB364:
	move.w	(a1)+,d0
	move.l	a1,$48(a0)           ; сохранить, где остановились
	cmpi.b	#$7E,d0
	blt.s	loc_2AB37A
	beq.s	loc_2AB37E           ; ровно $7E — просто остаться
	move.b	#$02,$5(a0)          ; больше $7E — подсостояние 2
	bra.s	loc_2AB37E
loc_2AB37A:
	move.b	d0,$4(a0)            ; меньше $7E — НОМЕР СОСТОЯНИЯ
```

Слово, у которого старший байт меньше `$80`, — **конец шага и новое
состояние**. Именно оно связывает программу с автоматом: программа не
«вызывает» состояние, а назначает его и отдаёт кадр. Значение `$7E`
означает «остаться», большее — «подсостояние 2», то есть цепочка
обработчиков.

Таблица `$2A64AE` — не длинные слова, а **четырнадцать `bra.w` подряд**
(`60 00 xx xx`), поэтому дизассемблер её не развернул; сами обработчики
лежат в `data_111` (`$2A64F4`-`$2A65C6`) и разобраны вручную.

| байт | размер | что делает |
|---|---|---|
| `$80 ff` + слово | 4 | байт поля `+$ff` = операнд |
| `$81 ff` + слово | 4 | слово поля `+$ff` = операнд |
| `$82 ff` + длинное | 6 | длинное поле `+$ff` = операнд |
| `$83 ff` + слово | 4 | поле из операнда = поле `+$ff` (копия слова) |
| `$84 00` + длинное | 6 | скрипт анимации `+$22` = операнд, `+$28` = 1, бит 11 в `+$30` |
| `$85 00` + слово | 4 | переход: `adda.w` операнда к указателю |
| `$86 nn` + слово | 4 | случайно: если `nn` меньше броска — дальше, иначе переход |
| `$87 ff` + слово | 4 | поле `+$ff` += операнд |
| `$88 ff` + слово | 4 | то же, но со знаком взгляда (бит 11) |
| `$89 ff` + слово | 4 | поле `+$ff` \|= операнд |
| `$8A ff` + слово | 4 | поле `+$ff` &= операнд |
| `$8B ff` + слово | 4 | поле `+$ff` ^= операнд |
| `$8C ff` + слово | 4 | если байт поля `+$ff` не ноль — переход |
| `$8D ff` + слово + слово | 6 | если байт поля `+$ff` равен первому операнду — переход |

Проверка на данных: все три программы крупного противника (`$1FEF54`,
`$1FEFDC`, `$1FF070`) разбираются этой таблицей без единого остатка, до
последнего байта, и все длинные слова `$84` попадают в окно скриптов
`$1D6E38`-`$1DB670`. Пример одной ступени:

```
$1FF070  84 00 00 1D 83 EE   скрипт <- $1D83EE
$1FF076  00 02               -> состояние 2, конец шага
$1FF078  80 26 00 0F         байт +$26 <- $0F
$1FF07C  84 00 00 1D 81 68   скрипт <- $1D8168
$1FF082  00 03               -> состояние 3, конец шага
$1FF084  81 16 FD 00         слово +$16 <- $FD00
$1FF088  81 18 FD 00         слово +$18 <- $FD00
```

Программы устроены **лесенкой**: ступень задаёт скрипт и состояние, а
`$85` в конце прыгает назад к началу лесенки. Три программы одного
противника — это одна и та же лесенка со сдвинутым началом, поэтому чем
дальше по ней, тем больше приёмов доступно. В `$1FF070` в самом низу стоит
развилка на `$86`:

```
$1FF174  86 54 00 12    случайно (порог $54) -> прыжок
$1FF178  86 80 00 26    случайно (порог $80) -> рывок
$1FF17C  84 00 00 1D 84 04 / 00 0D   иначе бросок (состояние 13)
```

То есть «какой приём выберет противник» — это не код, а три байта данных.

**В `coverage.py` из-за этого не хватало половины** (проверено, не
догадка): учитывалась только таблица `+$20`, и 1020 байт на мир оставались
без метки — около 8 КБ. Плюс последняя пара перелетала за `$28D000` на
146 байт, помечая код как данные. Исправлено: считаются обе таблицы, обе
по `256 * 4`, с зажимом по началу банка кода.

## Заявки главного цикла

Кроме сигнала выхода `$FF1A6C` главный цикл `$29806C` разбирает две
заявки. Обе устроены одинаково: взвести единицей, проверить, погасить.

**`$FF1394` — включить музыку уровня.** Взводится в четырёх местах
(`$298064` при входе в уровень, `$29812E`, `$298170`, `$2A0EAA`). Цикл
гасит её и запускает звук с номером из `$FF1B46`:

```asm
	tst.w	($FF1394).l
	beq.s	loc_2980B2
	clr.w	($FF1394).l
	jsr	(loc_296D16).l
	move.w	($FF1B46).l,d0   ; номер музыки уровня
	ext.l	d0
	jsr	(SoundStart).l
```

**`$FF213C` — показать заставку уровня.** Взводится в трёх местах
(`$298050`, `$298178`, `$2982AE`). Разбор интереснее: перед вызовом цикл
обнуляет `$FF1364`, а после смотрит, не появилось ли там что-нибудь, и если
появилось — вызывает как процедуру:

```asm
	tst.b	($FF213C).l
	beq.s	loc_2980DC
	clr.l	($FF1364).l      ; освобождаем слот продолжения
	jsr	(loc_28E970).l   ; собственно заставка
	clr.b	($FF213C).l
	tst.l	($FF1364).l      ; заставка что-то оставила?
	beq.s	loc_2980DC
	movea.l	($FF1364).l,a1
	jsr	(a1)             ; ...тогда зовём это
```

То есть `$FF1364` — **слот продолжения**: заставка может попросить
выполнить что-то после себя. Пишут туда ровно одно значение и ровно в одном
месте — `move.l #$0028EABE,($FF1364).l` в `$28E880`.

**`$FFFFFD82` — читают, но нигде не пишут.** На всю ROM одно обращение,
`tst.b` после возврата из кольца занятий. Не он один: соседи `$FFFFFD80`,
`$FFFFFD81` и `$FFFFFD84` тоже только читаются, по три-пять раз каждый.
Значит блок заполняет код, до которого обход не добрался, — это пункт 1
списка вопросов. (Проверено и отброшено: `$2F8C4E` и `$2F8C62`, которые
окружают опрос пультов, к блоку отношения не имеют — это захват и
освобождение шины Z80 через `$A11100`.)

## Кольцо занятий и сигнал выхода `$FF1A6C`

Это не тот список, что выше: у `$FFFFE166`/`$FFFFE176` свои операции, а
здесь отдельное кольцо со своим курсором.

| адрес | что |
|---|---|
| `$FF2184` | кольцо из восьми указателей на обработчики, 32 байта |
| `$FF2182` | курсор, шаг 4, перенос на `$20` |
| `$FF1A6C` | сигнал выхода: `0` — работаем, `+1` и `-1` — закончили |

`$298AB8` крутит кольцо: берёт указатель по курсору, пустой слот
пропускает, непустой вызывает, двигает курсор и **гасит отработавший
слот**. Перед каждым заходом проверяет `$FF1A6C`, и любое ненулевое
значение выводит из цикла:

```asm
loc_298AC4:
	tst.w	($FF1A6C).l
	bne.s	loc_298AF8     ; есть сигнал — выходим
loc_298ACC:
	movea.l	($0,a1,d0.w),a0
	cmpa.w	#$0000,a0
	beq.s	loc_298AC4     ; пусто — назад к проверке
	jsr	(a0)
	addq.w	#4,d0
	cmpi.w	#$0020,d0      ; перенос кольца
	bne.s	loc_298AEC
	moveq	#0,d0
loc_298AEC:
	move.w	d0,($FF2182).l
	clr.l	($0,a1,d1.w)   ; слот отработал — гасим
```

**Знак сигнала — это исход, а величина всегда единица.** На выходе код
берёт модуль, сравнивает с единицей и только тогда идёт на разбор; иначе
стоит `nop`. Знак при этом сохраняется отдельно, в `d1`:

```asm
loc_298AF8:
	move.w	($FF1A6C).l,d0
	move.w	d0,d1          ; знак остаётся здесь
	bpl.s	loc_298B04
	neg.w	d0
loc_298B04:
	cmpi.w	#$0001,d0
	beq.w	loc_298B0E
	nop                    ; других величин не бывает
```

Сходится с данными: за все 56 обращений в `$FF1A6C` пишут ровно три
значения — `$0001`, `$FFFF` и ноль.

`$298202` — «забрать и погасить»: кладёт флаг в `d0` и тут же обнуляет, то
есть отдаёт исход наверх ровно один раз. Пары `$290578`/`$2905E6` и
`$29071A`/`$2907EA` сохраняют флаг на стеке и восстанавливают — вложенная
сцена крутит своё кольцо, не затирая сигнал внешнего.

### Что означают знаки

Разбирает их `$298120`, и развилка не оставляет вариантов:

```asm
loc_298120:
	tst.w	($FF1A6C).l
	bpl.s	loc_298148         ; ПЛЮС -> уровень пройден
	jsr	(loc_296D16).l     ; МИНУС -> игрок погиб
	move.w	#$0001,($FF1394).l
	bsr.w	loc_2903A8
	bsr.w	loc_298394         ; остались ли жизни
	tst.w	d0
	beq.w	loc_29806C         ; да — переиграть ЭТОТ уровень
	bra.w	loc_297FE4         ; нет — в начало
loc_298148:
	...
	move.w	($FF1B14).l,d1
	cmpi.w	#$0012,d1
	blt.s	loc_298196
	jsr	(loc_28DCEC).l     ; уровень 18 — игра пройдена
	bra.w	loc_297FE4
loc_298196:
	...
loc_2981A6:
	move.w	($FF1B14).l,d1
	addq.w	#1,d1
	move.w	d1,($FF1B14).l     ; СЛЕДУЮЩИЙ уровень
```

| значение | что случилось | что дальше |
|---|---|---|
| `$0001` | **уровень пройден** | номер уровня плюс один; на 18-м (`$12`) — конец игры |
| `$FFFF` | **игрок погиб** | переиграть тот же уровень, а если жизней нет — в начало |
| `0` | ничего | кольцо крутится дальше |

Сходится с тем, кто их пишет. Единицу ставят объект выхода с уровня
(`$29C6D2`, см. [objects.md](objects.md)) и гнёзда боссов — `$2A778C`,
`$2A7BB2`, `$2A81BC`, `$2A95A2`, то есть **босс повержен**. Минус единицу
ставит утопление (`$2A17B0`, см. [terrain.md](terrain.md)) и `$2994A8`,
где счётчик `$FF214A` дошёл до дна.

Попутно: **игра кончается на уровне 18**, `MOJO STRONGHOLD`. Уровни 19-22
номер не увеличивают — они и не уровни, а бонус, куда попадают подменой
номера.

Ещё одно поле записи уровня получило смысл: `+$40` (в ОЗУ `$FF1B48`)
проверяется сразу после победы и включает показ чего-то между уровнями.

## Соглашение вызовов: это компилятор, а не человек

Код собран компилятором C. Признаки:

* аргументы кладутся **на стек** (`pea $XX.w`, `move.l $8(a6),-(a7)`), а
  не в регистры;
* вызов почти всегда абсолютный длинный: `jsr ($XXXXXX).l` — 1609 из 1687;
* после вызова стек чистит вызывающий: `lea $4(a7),a7` — 402 места;
* кадр стека через `link a6` встречается **дважды на всю ROM**: компилятор
  адресуется к аргументам прямо от `a7`, а `a6` заводит только там, где
  без него нельзя.

Практическое следствие для разбора: **`pea` перед `jsr` — это аргумент**,
и его значение обычно и есть номер звука, объекта или состояния.

Отсюда же и то, зачем анализатору понадобился отдельный проход по
одиночным указателям: компилятор складывает адреса процедур в структуры
данных, и обходом по коду до них не добраться.

## Диспетчеры

**Уровень.** `$28EE0E`: индекс `$FF1B14` (слово) умножается на 4 и
берётся из таблицы `$1FCC08` — это процедура инициализации уровня. Сразу
следом по тому же индексу берётся `$1FCBAC` — **буквы названия уровня для
заставки**, по шесть байт на букву до первого отрицательного слова. На
каждую заводится объект (`$29974C`), в него пишутся место (`+$12`, на
`$100` выше настоящего), настоящее место (`+$4C`) и скрипт анимации
(`+$22` = `$1D6D80 + номер глифа * 2`). Разбор и все девять названий —
в [graphics.md](graphics.md).

## Стопка предметов `$FF21FA`

Десять байт с длиной в отдельном слове. Каждый байт — номер предмета, и по
нему берут сразу из ДВУХ параллельных таблиц: `$1FE982` даёт скрипт
анимации, `$1FE992` — обработчик.

| адрес | что |
|---|---|
| `$FF21F8` | сколько занято, слово, не больше 10 |
| `$FF21FA` | сами байты, по одному на предмет |
| `$1FE982` | четыре скрипта анимации |
| `$1FE992` | четыре обработчика, ровно `+$10` от начала первой |

**Это стопка, а не очередь.** Кладут в конец и снимают с конца:

```asm
loc_29FEEC:				; положить
	lea	($FF21FA).l,a2
	move.w	($FF21F8).l,d0
	cmpi.w	#$000A,d0
	bge.s	loc_29FF0A     ; полна — байт молча теряется
	move.b	d7,($0,a2,d0.w)
	addq.w	#1,d0
	move.w	d0,($FF21F8).l
```

Переполнение не считается ошибкой: при десяти занятых процедура просто
выходит. Рядом `$29FF0C` — обёртка, кладущая предмет номер 0.

**Снятие** (`$2A000C`) делает больше, чем убавляет счётчик: играет звук 2,
ставит в `$A(a0)` таймер `$5A`, а потом, если стопка не опустела, читает
НОВЫЙ верхний байт и достаёт его скрипт из `$1FE982`. Опустела — выставляет
`$FF1A6C` в `$FFFF`.

**Обход всей стопки** идёт в двух местах и по разным таблицам: `$28ECB8`
берёт скрипты из `$1FE982` и порождает объекты, `$29FEC2` берёт обработчики
из `$1FE992` и вызывает каждый. Обнуляют стопку `$28EC08` и `$2A603A`,
причём второй — вместе с зарядом броска `$FF04E4`.

Тринадцать обращений к паре `$FF21F8`/`$FF21FA` объяснены все.

**Чем предметы являются по смыслу — не доказано.** Против инвентаря то, что
видов всего четыре и стопка чистится вместе с зарядом; за — звук при
снятии, показ верхнего предмета и флаг «кончились». Похоже на переносимый
боезапас, но это догадка, а не разбор.

## Разбег и бросок: одна и та же величина

Раньше `$FF04E4` назван здесь «накопителем заряда». Это верно, но узко:
та же ячейка — **скорость разбега**, и бросок просто берёт её как
величину. Полный разбор `loc_292DE2` не оставляет вариантов.

| адрес | что |
|---|---|
| `$FF04E4` | **величина разбега**, она же заряд при броске |
| `$1EABC2` | прибавка за кадр: 14, 27, 42, 53 и **ноль** пятым |
| `$1EABAE` | пять единичных векторов направления, формат 1.15 |

**Накопление, и чем оно управляется.** Индекс в `$1EABC2` — не счётчик
шагов, а **сила поверхности под ногами**: `loc_292C46` отдаёт 0..3 для
кодов местности `$3C`..`$43` и **4**, когда такой поверхности нет (см.
[terrain.md](terrain.md)).

```asm
	bsr.w	loc_292C46
	lea	($1EABC2).l,a1
	add.w	d2,d2
	move.w	($0,a1,d2.w),d1      ; прибавка по силе поверхности
	eor.w	d0,d1
	sub.w	d0,d1                ; знак — от взгляда и направления полосы
	move.w	d1,d3
	add.w	($FF04E4).l,d1
	tst.w	d3
	bne.s	loc_292E24
	cmpi.w	#$0200,d1
	bgt.s	loc_292E32
	move.w	#$0200,d1            ; на обычной земле — ровно шаг
	bra.s	loc_292E32
loc_292E24:
	tst.w	d1
	beq.s	loc_292E2A
	bpl.s	loc_292E32
loc_292E2A:
	bchg	#11,(a0)             ; разогнали в другую сторону — развернуться
	neg.w	d1
```

Пятая запись таблицы — **ноль**, и это вся суть: **на обычной земле разбег
не растёт**, зажим держит `$0200`, то есть обычный шаг. Разгоняются только
на особых полосах, а если полоса гонит против взгляда, величина уходит в
минус — и игрок разворачивается.

**Направления.** В `$1EABAE` пять пар слов, и длина каждой ровно единица
(проверено: 0.9999–1.0000). Углы — 14.0, 26.6, 45.0, 63.4 и 180.0 градусов.
Второй столбец пары иногда адресуют отдельно как `$1EABB0`; это не другая
таблица.

**Запуск.** `$292C7E` зажимает величину в `$0800`, кладёт её в `$FF04E4` и
считает скорость обычным умножением в неподвижной точке — `mulu`, удвоение,
`swap` за старшим словом:

```asm
	cmpi.w	#$0800,d1
	blt.s	loc_292C88
	move.w	#$0800,d1      ; зажим величины
loc_292C88:
	move.w	d1,($FF04E4).l
	lea	($1EABAE).l,a1
	add.w	d2,d2
	move.w	($0,a1,d2.w),d3  ; косинус, 1.15
	mulu.w	d1,d3            ; направление * величина
	add.l	d3,d3            ; 1.15 -> 1.16
	swap	d3               ; старшее слово и есть ответ
	move.w	d3,$16(a0)       ; скорость по горизонтали
	move.w	($2,a1,d2.w),d3  ; синус
	mulu.w	d1,d3
	add.l	d3,d3
	swap	d3
	eor.w	d0,d3            ; d0 = 0 или -1:
	sub.w	d0,d3            ; отражение по вертикали
	move.w	d3,$18(a0)       ; скорость по вертикали
```

Пара `eor`/`sub` с маской `0` или `-1` в `d0` — обычный способ взять или не
взять обратный знак без ветвления. Вторая площадка, `$29302E`, делает то же
самое, только величину берёт из `d4`.

**Разворот.** `$2931B4` и `$2931C2` переключают бит 11 в `(a0)` — тот самый
флаг отражения по горизонтали — и, **только если бит и правда изменился**,
делают `neg.w ($FF04E4)`. Пары `bclr`/`beq` и `bset`/`bne` нужны именно для
этого: повторный вызов в ту же сторону знак не трогает.

**Затухание.** `$29FE16` при отрицательном `d2` (отскок) гасит `$5(a0)`,
обнуляет горизонтальную скорость напарника `$16(a1)`, делит заряд пополам
через `asr.w ($FF04E4)` и переводит объект на скрипт `$1DB604`. То есть
каждый отскок теряет половину силы.

**Сброс и проверка.** `$2930A4`, `$2931D0` и `$2A6034` обнуляют `$FF04E4`
(последний — вместе с `$FF21F8`); `$29FE4A` выставляет готовое значение
`$0600`; `$292FC4` и `$293080` проверяют накопитель на ноль, чтобы понять,
идёт бросок или нет.

Всего к `$FF04E4` обращаются восемнадцать раз, и все восемнадцать
объяснены: пять записей, три обнуления, разворот, затухание, предустановка
и восемь чтений.

Поля `+$16`/`+$18` записи объекта — это и есть скорость, длинным словом
сразу обе половины ([open-questions.md](open-questions.md), пункт 8).

## Заставка уровня

`$28EE02` строит её из двух частей. Сначала зовёт **процедуру мира** из
`$1FCC08` — она короткая и одинаковая по форме:

```
lea <скрипт сцены>,a1 ; bsr $28E654
lea <актёры>,a2       ; bsr $28E73A
```

Список актёров (`$28E73A`) — слово-счётчик, дальше по **двенадцать байт**:
x, y, скрипт анимации, обработчик. Координаты экранные, и почти все актёры
начинают за краем (`x = -16` или `336`), то есть входят в кадр. Списков
девять, по одному на мир, лежат в `$1EA35C`-`$1EA5D8`.

Потом на каждую букву названия заводится свой объект — см. ниже.

```bash
make levels LEVEL="--scene 7"
```

**Поправка к своду.** Вопрос «где лежит расстановка объектов уровня»
поставлен был неверно: `$1FCC08` — это не расстановка в игре, а сцена
заставки. Внутриигровые объекты берутся только из клеток карты (байт `+3`
свойств клетки), другой расстановки в данных нет.

## Текст: две таблицы ширин, одна из них у мёртвого печатника

`$1EA852` и `$1EA5FE` — **таблицы ширин знаков**, по 64 записи, индекс
`знак - $20`, то есть `$20`..`$5F`. Обе устроены одинаково:

| таблица | пробел | остальные | строка | кто пользуется |
|---|---|---|---|---|
| `$1EA5FE` | 8 | **12** | 16 точек | живая: `$28E594`, ввод пароля `$290620` |
| `$1EA852` | 8 | **16** | 24 точки | `$28F9C6`, и больше никто |

То есть шрифт **моноширинный**: возможность разной ширины в таблицу
заложена, но ни один знак ею не пользуется — кроме пробела, который вдвое
уже.

Печатник `$28F9C6` разбирает готовый формат:

```asm
	move.b	(a2)+,d7         ; сколько строк
	move.w	d7,d0
	lsl.w	#2,d0
	move.w	d0,d1
	lsl.w	#1,d0
	add.w	d1,d0            ; d0 = 12 * строк
	moveq	#112,d2
	sub.w	d0,d2            ; ЦЕНТР ПО ВЕРТИКАЛИ — 112
loc_28F9E8:
	move.b	(a2),d0
	bpl.s	loc_28F9F2
	addq.l	#1,a2
	move.b	(a2)+,d5         ; байт со взведённым старшим — признак строки
loc_28F9F2:
	jsr	(loc_28F9A8).l   ; сложить ширины
	lsr.w	#1,d0
	move.w	#$00A0,d1
	sub.w	d0,d1            ; ЦЕНТР ПО ГОРИЗОНТАЛИ — 160
```

Строка кончается нулём, следующая идёт на 24 точки ниже.

**А зовут его ниоткуда.** Ни одной ссылки в коде и ни одного длинного
слова в ПЗУ, равного `$28F9C6`. При этом его соседи живы: складыватель
ширин `$28F9A8` зовут из трёх мест, рисователь знака `$28F940` — тоже из
трёх. То есть многострочный центрованный вывод из игры выпал, а мелкие
части его машинерии остались в деле.

Что осталось от текста живого: `$290620` рисует девять знаков от
(`$58`, `$B8`) с шагом 16 и ещё шесть от (`$70`, `$C8`), каждому ставя
`+$27 = 3` — это **ввод пароля**.

## Пароли и меню DEBUG

Экран ввода пароля — `$29098C`. Пароль всегда **шесть букв** `A`-`Z`,
буфер ввода `$FF0016`, курсор ходит по кругу от 0 до 5.

### Пароли уровней

Таблица `$1FCB26`, семь записей по шесть байт: слово номера и длинное
слово-указатель на строку. Сравнение прямое, совпадение кладёт
`слово + 1` в `$FF1B14` и играет звук `$31`.

| пароль | уровень | куда |
|---|---|---|
| `ININJA` | 3 | NINJA TRAINING GROUNDS |
| `ILVMUD` | 7 | MUDDRAKE MAYHEM |
| `ITSHOT` | 10 | THE SACRIFICE OF MAUI |
| `GETHIM` | 12 | THE TEST OF DUCKHOOD |
| `YOHOHO` | 14 | THE FLYING DUCKMAN |
| `UNDEAD` | 16 | THE REALM OF THE DEAD |
| `GDLUCK` | 18 | MOJO STRONGHOLD |

Что разбор верен, видно без эмулятора: каждый пароль подходит своему
уровню по смыслу — `ILVMUD` к грязевым, `ITSHOT` к вулкану, `UNDEAD` к
царству мёртвых, `GDLUCK` к последнему оплоту.

### Чит на DEBUG

Два пароля вводятся **по очереди**, и хранятся они **со сдвигом на
единицу**: `$290A66` сравнивает введённую букву плюс один. `$1EAA27`
содержит `JNDBSZ`, то есть вводить надо **`IMCARY`**; после него
`$FF0010` становится 1 и проверяется `$1EAA2E` — `NBVJNN`, то есть
**`MAUIMM`**. Совпало — `$FF2180 = 1` и звук `$33`.

Дальше `$2908FA` берёт описатель главного меню по этому байту: обычно
`$1FD440` (`START`, `OPTIONS`, `PASSWORD`), а при `$FF2180` — `$1FD46E`,
где есть ещё и `DEBUG`. Так закрывается вопрос «чем выбирается вариант
меню».

В самом меню DEBUG: `ENEMY COLL` (ON/OFF), `GAME FLOW` (ON/OFF),
`MAP MODE` (OFF/ON) и выбор уровня — **23 коротких названия**, и их
порядок слово в слово повторяет таблицу уровней:

```
MOJO MANSION-1..3   N TRAINING -1..3, B   MD MAYHEM -1..3
VOLCANO -1..2       DUCKHOOD -1..2        DUCKMAN -1..2
ZOMBIES -1..2       STRONGHOLD-1          LUAU - ACT 1..4
```

Это третье независимое подтверждение, что уровней ровно 23, и заодно
перевод названий заставки на язык разработчиков: «THE SACRIFICE OF MAUI»
у них `VOLCANO`, «THE REALM OF THE DEAD» — `ZOMBIES`.

```bash
make levels LEVEL=--passwords
```

Обработчики пунктов меню лежали в `bin` (`$29080E`-`$290BB8`, 938 байт):
адреса берутся из описателей меню, обход по потоку управления туда не
доходит. Переведены в код руками, пересборка осталась побайтовой.

## Три формы игрока

Главная механика игры — смена костюма — держится на одном слове в ОЗУ,
`$FF133A`. Оно выбирает **две таблицы разом**: скрипты анимации и
обработчики действий.

| `$FF133A` | скрипты `$FF1336` | обработчики `$FF1332` | высота `$FF133C` | кто |
|---|---|---|---|---|
| 0 | `$1FCC64`, 11 | `$1FCCE0`, 46 | `$20` | Maui Mallard, утка |
| 1 | `$1FCC90`, 10 | `$1FCD98`, 46 | `$20` | Cold Shadow, ниндзя |
| 2 | `$1FCCB8`, 10 | `$1FCE50`, 46 | `$10` | уменьшенный |

Три набора скриптов лежат **встык одним куском** `$1FCC64`-`$1FCCE0`, три
набора обработчиков — так же, `$1FCCE0`-`$1FCF14`. Ставят их три
процедуры:

* `$291B60` — утка, `$291B84` — ниндзя. Обе просто пишут пару указателей
  и `$FF133A`. Зовут их со всех сторон: подбор значка превращения
  (`$2A9082`, звук `$2F`), загрузка уровня (`$2986AC` — форма
  восстанавливается), концовки этапов;
* `$29A8A0` — **переключатель** обычной и уменьшенной формы. Он же
  проигрывает превращение: кладёт в `$FFFFE1EC` скрипт `$1D7E8E`
  (уменьшиться) или `$1D7EE4` (вырасти), а это кадры 255-272 — Дональд
  сплющивается. Форму 1 он не трогает: `cmpi.w #1,d2; beq` и выход, то
  есть ниндзя уменьшаться не умеет.

Высота `$FF133C` не для красоты: её прибавляют к координате в пробе земли
(`$2A4F...`), поэтому уменьшенный Дональд и стоит, и пролезает иначе.

Что форма 1 это именно ниндзя, видно по кадрам: у формы 0 первые кадры
скриптов — 63, 94, 108 (утка в красной жилетке), у формы 1 — 431, 498, 530
(чёрное ги с красным поясом), у формы 2 — 2350 и 2413 (крошечный Дональд).

```bash
make anim ANIM=--forms
```

**Состояние игрока.** `$2A4EE0`: индекс `$FF2130` (байт) — таблица
`$1FD014`, 273 записи. Вокруг вызова видно работу с полями `+$18`
(скорость по вертикали: к ней прибавляют `$3C`, а в особом случае `$0C`)
и битами `$30(a0)`; `$FF2131` при этом сравнивается с 1, а `$FF2132`
служит набором флагов.

## Палитра: плавный переход за 16 кадров

`$290C70` принимает в `a0` палитру из 64 слов (`0BGR`, четыре ряда по 16
цветов) и запускает переход:

1. каждый цвет раскладывается по нибблам маской `$0F0F` — отдельно
   красный и зелёный+синий;
2. разница с текущей палитрой `$FFFFDC40` делится на 16 (`asr.l #4`) —
   получается шаг на кадр;
3. пары «текущее значение, шаг» ложатся в `$FFFFDCC2`;
4. в короткий список обработчиков кадра добавляется `$290CBC`, который
   16 раз (`$FFFFDEC2`) досыпает шаг и пишет CRAM командой `$C0000000`;
5. на время перехода поднят флаг `$FFFFDCC0` — главный цикл на нём ждёт
   (`$298154`).

Палитры в ROM лежат без сжатия, подряд 64 словами.

## Передачи в VRAM

Отдельная тема со своим документом: очередь DMA, разгребатель из ОЗУ,
рукопожатие со звуковым процессором и то, откуда берутся тайлы, —
[graphics.md](graphics.md).

## Анимация тайлов: `$FFFFFC70`

Считалось, что этот буфер заполняют и не читают. Читатель лежит **прямо
под заполнителем**, следующей же процедурой.

Заполняет `loc_2973BA`: берёт `d0` записей по 8 байт и кладёт каждую
**дважды**:

```asm
loc_2973BA:
	move.w	d0,($FFFFFC6E).w
	lea	($FFFFFC70).w,a1
loc_2973C6:
	move.l	(a0)+,d1
	move.l	(a0)+,d2
	move.l	d1,(a1)+
	move.l	d2,(a1)+
	move.l	d1,(a1)+      ; та же восьмёрка ещё раз
	move.l	d2,(a1)+
	dbf	d0,loc_2973C6
```

Удвоение — не избыточность, а приём: **первая копия хранит постоянные, вторая
работает**. Видно по читателю `loc_2973D8`:

```asm
	move.w	($FFFFFC6E).w,d7
	lea	($FFFFFC70).w,a0
loc_2973E4:
	subq.w	#1,$E(a0)             ; рабочий счётчик (копия 2)
	bne.s	loc_29741A
	move.w	$6(a0),$E(a0)         ; перезарядить из ПОСТОЯННОЙ (копия 1)
	movea.l	$8(a0),a1
	...
	move.w	(a1)+,d0              ; длина
	move.l	(a1)+,d1
	lsl.l	#1,d1                 ; адрес хранится СЛОВНЫМ
	move.w	(a1)+,d5
	bsr.w	loc_296078            ; передача
	subq.w	#1,$C(a0)
	bne.s	loc_297416
	move.w	$4(a0),$C(a0)         ; второй счётчик так же
```

Исходная запись, стало быть: длинное слово — список передач, два слова —
два счётчика. Список передач по 8 байт: длина, словный адрес, приёмник.

Зовёт `loc_2973D8` **`AnimStep`** (`$297022`), то есть тайлы тикают в том
же проходе, что объекты.

А заполняют его из трёх мест, и одно из них называет ещё два поля записи
уровня:

```asm
	move.w	($FF1B24).l,d0    ; поле +$3A — сколько записей
	movea.l	($FF1B26).l,a0    ; поле +$18 — сама таблица
	jsr	(loc_2973BA).l
```

Прочие два — заставка (`$1E9672`, одна запись) и сброс в ноль.

## Отладочная проверка очереди DMA

`$299604` проходит по очереди `$FF07AC` и у каждой записи сверяет слово в
`+6` с `$FFFFE138`; если больше — `illegal`, то есть намеренный вылет:

```asm
	move.w	(a0)+,d0
	adda.l	#$00000004,a0
	move.w	(a0)+,d1
	cmp.w	d3,d1
	bhi.s	loc_29962C
	beq.s	loc_29962C
	illegal
```

**Ссылок на неё нет ни одной** — ни команды, ни длинного слова. Это
отладочное утверждение, которое осталось в готовой игре, но никем не
вызывается.

## Пульт: переназначение кнопок

`$1FD7AC` — **таблица раскладок пульта**, шесть наборов по 8 байт. Выбирает
набор байт `$FFFFFD7B`:

```asm
loc_2984A4:
	moveq	#0,d0
	move.b	($FFFFFD7B).w,d0
	lsl.w	#3,d0                ; * 8
	move.l	#$001FD7AC,d1
	add.l	d0,d1
	move.l	d1,($FFFFFD74).w     ; выбранная раскладка
```

Применяет её `$295E26`, и видно ровно, что она делает:

```asm
loc_295E26:
	movea.l	($FFFFFD74).l,a1
	move.w	d0,d1
	andi.w	#$0070,d1            ; биты A, B, C
	lsr.w	#4,d1
	move.b	($0,a1,d1.w),d1      ; -> новое сочетание
	andi.b	#$8F,d0              ; крестовина и Start как были
	or.b	d1,d0
```

Маска `$8F` оставляет нетронутыми крестовину (биты 0-3) и Start (бит 7), а
переставляются только три кнопки. Таблица это подтверждает — все шесть
наборов суть перестановки одних и тех же восьми сочетаний:

| набор | байты |
|---|---|
| 0 | `00 20 10 30 40 60 50 70` |
| 1 | `00 20 40 60 10 30 50 70` |
| 2 | `00 40 10 50 20 60 30 70` |
| 3 | `00 10 40 50 20 30 60 70` |
| 4 | `00 40 20 60 10 50 30 70` |
| 5 | `00 10 20 30 40 50 60 70` — **тождественная** |

Шесть наборов по 8 байт кончаются на `$1FD7DC`, дальше уже другие данные.
Результат уходит в `$FFFFE1C6`/`$FFFFE1C7`/`$FFFFE1C8` — привычная тройка
«держат / нажали / отпустили».

### Настройки `$FFFFFD78`-`$FFFFFD85`: читают, но не пишут

Рядом с номером раскладки лежат ещё байты, и все они той же природы:

| байт | где читают |
|---|---|
| `$FD7B` | номер раскладки пульта (`$2984A6`) |
| `$FD7C` | `$29842A` |
| `$FD80` | `$298498` |
| `$FD81` | пять мест: `$299928`, `$299982`, `$299A0E`, `$29C0BE`, `$29FFF8` |
| `$FD82` | `$2980FA` |
| `$FD84` | четыре места: `$298D12`, `$298DE0`, `$2A4D8A`, `$2A5040` |

**Ни один из них никто не пишет**, и адрес этого блока нигде не берут
(`lea` на `$FFFFFD7x` во всём коде нет). То есть это не отдельная загадка
`$FFFFFD82`, как считалось раньше, а весь блок целиком.

Раз не пишут — значит там всегда ноль, и каждое из тринадцати чтений
всегда идёт одной и той же веткой. А по тому, ЧТО эти ветки делают,
назначение байтов читается:

| байт | что с ним делают | при нуле |
|---|---|---|
| `$FD7B` | номер раскладки пульта | раскладка **0** |
| `$FD7C` | индекс в таблицу, `lsl #3`, результат в `$FF1346`/`$FF1348` | первая запись |
| `$FD80` | `move.w d0,($FF1B14)` — **прямо в номер уровня** | начать с нулевого |
| `$FD81` | `tst.b; bne` перед расчётом урона (`$299928`) | урон считается |
| `$FD82` | `tst.b; beq` в начале кольца (`$2980FA`) | пропустить ветку со звуком |
| `$FD84` | `tst.b; bne` в двух местах (`$298D12`, `$2A4D8A`) | обычная ветка |

То есть это **блок отладочных настроек**: с какого уровня начать,
считать ли урон, какая раскладка кнопок. В готовой игре его не заполняет
никто, и все настройки стоят в нуле.

Одна мелочь стоит отдельного слова. Раскладка 0 — это
`00 20 10 30 40 60 50 70`, и она **не тождественная**: индекс 1 (`$10`,
кнопка B) даёт `$20`, индекс 2 (`$20`, кнопка C) даёт `$10`. Тождественная
лежит под номером 5. То есть в готовой игре **B и C переставлены местами**
относительно сырого байта пульта.

## Пул объектов: 80 записей по `$54`

`$295E7E` раскладывает пул целиком, и из восьми команд видно всё:

```asm
loc_295E7E:
	lea	($FFFFE1CA).w,a0
	clr.w	($FFFFE1C2).w      ; список занятых пуст
	move.w	a0,($FFFFE1C0).w   ; голова свободных
	moveq	#79,d0
loc_295E8C:
	movea.w	a0,a1
	adda.w	#$0054,a0          ; ШАГ ЗАПИСИ
	clr.w	(a1)               ; слово флагов = ноль = свободна
	move.w	a0,$2(a1)          ; связь по +$2
	dbf	d0,loc_295E8C
	clr.w	$2(a1)
```

| | |
|---|---|
| размер записи | **`$54` = 84 байта** |
| записей | **80** |
| пул | `$FFFFE1CA`-`$FFFFFC0A` |
| запись 0 | **игрок** — оттого `$FFFFE1CA` везде и значит «игрок» |
| `$FFFFE1C0` | голова свободных |
| `$FFFFE1C2` | голова занятых |

Размер сходится с разбором полей: самое дальнее поле записи — `+$52`
(границы патрулирования, слово), и оно кончается ровно на `+$54`. Проверено
по всему дизассемблеру: **обращений к смещениям больше `+$52` нет ни
одного**, кроме `+$C8`, а это не запись объекта, а `GfxSetAlloc` со своими
слотами по 200 байт.

Пара голов лежит встык нарочно. Вставка идёт от **поддельной записи**: в
`$295FA6` берётся адрес `$FFFFE1C0` как будто это объект, и его «следующий»
(`+$2`) приходится ровно на `$FFFFE1C2` — голову занятых. Так обход не
разбирает отдельно случай «вставить в начало».

### Хвост записи: две пары `+$4C`/`+$4E` и `+$50`/`+$52`

Последние восемь байт записи долго числились безымянными. Считать их
«черновиком» неверно: **восемнадцать мест читают и пишут их парами**
через `movem.w`, то есть это ТОЧКИ, а не отдельные слова.

```asm
$2A2A60  movem.w $4C(a0),d0/d1
$2A7D94  movem.w $4C(a0),d0/d1
$2AB03C  movem.w d0/d1,$4C(a0)
$2A894C  movem.w $50(a0),d0/d1
$2AB5F6  movem.w $50(a0),d1/d2
```

Сходится с разобранным: `+$50`/`+$52` у летуна — центр окружности, у
патрульного — границы, а `+$4C`/`+$4E` у рывка — цель. Часть видов ломает
пару и берёт слова порознь (`+$4C` как фазу в `$2A32AA`, `+$4E` как заявку
от скрипта у крупного противника) — но это исключение, а не правило.

По числу обращений: `+$4C` — 299, `+$50` — 193, `+$4E` — 115, `+$52` — 73.
То есть `+$4C` самое ходовое поле хвоста.

### Что в записи ещё без имени

| поле | обращений | что известно |
|---|---|---|
| `+$27` | 21 | **навязанный ряд палитры плюс один.** `$296192` кладёт `+$27 - 1` в младший байт `d7`, `ror.w #3` двигает это в биты 13-14, а `$29621C` стирает ряд из кадра (`andi.w #$9FFF`) и подставляет свой. При нуле `subq.b #1` даёт `$FF`, `tst.b` видит минус — подмена пропускается, остаётся ряд кадра |
| `+$1A`, `+$1B` | 12 и 12 | **дробные остатки движения**, по байту на ось |
| `+$46` | 9 | **маска задетых коробок** |
| `+$03`, `+$07`, `+$0E`, `+$11`, `+$38`, `+$3A` | по 1-8 | единичные обращения |

### Дробные остатки `+$1A` и `+$1B`

Скорость лежит в `+$16`/`+$18` в формате 8.8, а положение — целое. Куда
девается дробная часть, видно в `$29A9AA`:

```asm
	moveq	#0,d4
	move.w	$18(a0),d0       ; скорость по вертикали
	bpl.s	loc_29A9B2
	subq.w	#1,d4            ; знак в старший байт
loc_29A9B2:
	move.b	$1B(a0),d4       ; накопленная дробь
	add.w	d0,d4
	move.b	d4,$1B(a0)       ; сохранить обратно
	asr.w	#8,d4            ; целая часть
	bpl.s	loc_29A9C2
	addq.w	#1,d4            ; округление к нулю
loc_29A9C2:
	...
	add.w	d4,$14(a0)
```

Тот же кусок парой выше работает с `+$1A` и `+$12`. То есть **`+$1A` и
`+$1B` — накопители дробной части по горизонтали и вертикали**, по байту
на ось, и живут они между кадрами. `$2A7E00 clr.w $1A(a0)` гасит оба разом.

### Маска задетых коробок `+$46`

Лежит рядом с `+$42` (накопленный удар) и `+$44` (тип удара) и набирается
там же:

```asm
	move.b	$42(a1),d0
	bne.s	loc_294B46
	clr.w	$46(a1)          ; первый удар за кадр — сбросить
loc_294B46:
	add.b	$43(a0),d0
	move.b	d0,$42(a1)
	...
	jsr	(loc_2964DA).l   ; проверка коробок
	tst.w	d7
	beq.s	loc_294B70
	or.w	d6,$46(a1)       ; КУДА попали
```

А `loc_2964DA` показывает, откуда берутся биты, и заодно подтверждает
раскладку кадра со стороны столкновений:

```asm
	movea.l	$C(a1),a2        ; кадр
	move.w	(a2)+,d6
	addq.w	#1,d6            ; кусков
	move.w	(a2)+,d7         ; коробок
	...                      ; d6 * 10 + 4 — пропустить куски и четвёрку байт
	adda.w	d6,a2
	...
	move.w	$4(a2),d4
	bset	d4,d7            ; НОМЕР КОРОБКИ — это номер бита
```

Шаг куска 10 байт и четыре байта в `+4` тут пересчитываются независимо от
разбора графики и сходятся с ним. А слово-номер коробки, которое в
`tools/frames.py` значилось просто «номером», оказывается **номером бита**
в маске.

Разбирает маску один вид: `$2A30FC` смотрит бит 14 и, если попали туда и
игрок правее, толкает объект вправо скоростью `$0200`.

### Флаги `+$30`

Слово `+$30` — второй набор флагов объекта. Биты 8-14 адресуют через
`+$30` (старший байт), биты 0-7 — через `+$31`; на 68000 битовые команды
по памяти байтовые и номер берут по модулю 8, поэтому `bset #14,$30(a0)`
это бит 6 старшего байта, он же бит 14 слова.

| бит | что значит | чем доказано |
|---|---|---|
| **14** | «обходить стороной» | шесть проверок, и все пропускают объект: перебор графики `$2963E0`, уборка со смертью `$2A2A28`, порождение `$2A4EF6`. Ставят перед рывком (`$2A9DCC`) и снимают по прибытии (`$2A9DFE`), ставят перед самоснятием (`$2AB216`) |
| **12** | **считается в квоте порождения**, и он же — мишень бомбы | `loc_29E1FE` пробегает список и считает объекты с этим битом, а все девять вызывающих сравнивают итог с пределом: не больше 1 (`$29E04E`), 3 (`$29E242`), 4 (`$29E73E`, `$29E76C`), 2 (`$2A1688`) или ни одного (`$2A4120`). А `loc_2957E4` по тому же биту раздаёт предельный урон всем сразу — см. [player.md](player.md) |
| **13** | то же, вторая квота | `loc_2A370C` считает так же, и `$2A3772` порождает, только если ноль |
| **2** (в `+$31`) | **при смерти выронить предмет** | проверяют `loc_299CF8` (общая смерть) и два места в `$2AB2xx`, и все три зовут `loc_299D70` — а тот порождает вид `$22` со скоростью `$FD00` вверх, скрипт `$1DAFB0` |
| **3** (в `+$31`) | не снимать при общей уборке | `$298B34`: при поднятом бите обход пропускает `loc_2997B2` |
| 8, 9, 10, 11 | не установлены | `bclr #11` встречается 25 раз, `bset #10` семь, но ни одной ПРОВЕРКИ — читателя у них нет |
| 5 (в `+$31`) | не установлен | проверяется один раз, в коде игрока рядом с `$FF133A` |

Квота — самая заметная из них: **генераторы отказываются выпускать
очередного, пока живы предыдущие**. Отсюда и ощущение, что противники на
уровне не накапливаются.

## Ключ `+$10` — порядок рисования

Список занятых держат **отсортированным по `+$10`**, вставкой:

```asm
loc_295FD2:
	move.w	$2(a1),d1
	beq.s	loc_295FE4
	movea.w	d1,a2
	cmp.w	$10(a2),d0
	ble.s	loc_295FE4         ; нашли место
	movea.w	d1,a1
	bra.s	loc_295FD2
loc_295FE4:
	move.w	d0,$10(a0)
	move.w	d1,$2(a0)
	move.w	a0,$2(a1)
```

Порядок возрастающий: идём, пока новый ключ больше, и встаём перед первым,
чей ключ не меньше.

**Что этот порядок значит.** По списку ходят ровно две вещи, и обе от одной
головы `$FFFFE1C2`:

| кто | что делает |
|---|---|
| `AnimStep` (`$297010`) | зовёт `+$1E` каждого и крутит анимацию: `+$28`, `+$22`, `+$26` |
| сборщик таблицы спрайтов (`$296158`) | складывает куски в `$FF050C` и шлёт в VRAM |

Порядок в таблице спрайтов Mega Drive и есть порядок рисования: кто раньше
в списке, тот поверх. Значит `+$10` — **глубина**, и меньший ключ
означает «ближе к зрителю». Порядок обновления достаётся тем же списком
заодно, а не наоборот.

Косвенное подтверждение: `$296DFE` копирует ключ родителя в часть
(`move.w $10(a6),$10(a0)`) — сборный объект должен рисоваться слитно.
Зовут вставку из четырнадцати мест.

## Объекты: списки, связанные словом

Адреса объектов хранятся **словами**: ОЗУ Mega Drive лежит в
`$FF0000-$FFFFFF`, поэтому `movea.w` со знаковым расширением превращает
`$E1CA` обратно в `$FFFFE1CA`. Ноль означает «конца списка нет».

* `+$2` записи — следующий в списке;
* `+$10` — ключ, по которому список держат отсортированным;
* `$295EA2` и `$295EF6` переставляют запись в списке по этому ключу,
  голова — `$FFFFE1C0`;
* `$29974C` и `$299780` создают объект: зовут `$295EA2`, потом `$2996C2`,
  и возвращают `a0` = запись либо `movea.w #0,a0` при отказе.

Что именно упорядочивает ключ `+$10` — порядок отрисовки, приоритет
обновления или что-то третье — **не установлено**.

## Запись объекта: все $54 байта названы

```
python tools/objects.py --record
```

Перепись идёт по банку кода: каждое обращение вида `$NN(aX)` со смещением
не больше `$53` попадает в счёт, а инструмент сверяет его с раскладкой и
ругается на безымянное. Сейчас **названы все 50 смещений, к которым
обращается код**, и обращений дальше `+$52` нет вовсе — это и есть
доказательство размера `$54`.

Последними легли пять полей:

| поле | что | чем доказано |
|---|---|---|
| `+$1C` | **очки жизни** | конструкторы кладут туда 1, 2, 4, 6, 8, `$0C`, `$10`, `$14`, `$3C`, `$5A`, а `$2A2C74` вычитает из него удар |
| `+$2A` | **номер клетки карты** | читает его `ObjectReleaseCell` (`$2918BA`) и при нуле возврат пропускает; пишется в `$2996C2` рядом с `+$2C`/`+$2E`, то есть вместе с координатами клетки |
| `+$32`, бит 0 | отметка разбора касания | ставят как `bset #8,$32(a1)` в четырёх местах разбора удара (`$299B1A` и соседи), проверяют как `btst #8,$32(a0)` в пяти обработчиках; по единице объект уходит в `loc_299CC6` вместо обычного шага |
| `+$38` | свободное слово | гасится при постройке (`move.l d5,$38(a0)`), а пользуется им ровно один объект — `$2A0380` крутит там фазу 0-1 каждые четыре кадра |
| `+$43` | **урон, который объект НАНОСИТ** | `move.b $43(a0),$42(a1)` в четырёх местах: своё `+$43` уходит в чужое `+$42`, накопленный удар. Конструкторы ставят 1, 2, 4, 5, `$0A`, `$10`, `$25` |

**`+$3A` объяснило поле `+$C`.** Кадр в `+$C` — длинное слово, и обычно
это адрес в картридже. Но `$296FCC` собирает его иначе:

```asm
	move.l	#$FFFFFFFF,d0
	move.w	$3A(a0),d0
	move.l	d0,$C(a0)
```

То есть в старшее слово кладут `$FFFF`, в младшее — `+$3A`, и выходит
`$FFFFxxxx`. У 68000 адрес 24-битный, верхний байт отбрасывается, так что
это обычный адрес в ОЗУ `$FFxxxx`. Никакой метки здесь нет — это просто
короткий адрес, расширенный до длинного. Сам кадр строит `$298F2A`: копирует
девять слов из `$1E9260` в ОЗУ и правит последнее длинное слово на
`адрес / 2` — источник для передачи DMA.

**Пять смещений оказались чужими.** `+$3`, `+$E`, `+$11`, `+$20` и `+$24`
в коде встречаются, но по другой базе: запись сценки по четыре байта,
запись анимации тайлов `$FFFFFC70`, буфер распаковщика, запись уровня и
таблица VSRAM `$FF20E0`. В записи объекта их нет, и `--record` помечает их
отдельно, чтобы перепись не выглядела дырявой.

## Затемнение экрана: палитра из одних нулей

`loc_290C54` гасит экран и ждёт конца перехода:

```asm
loc_290C54:
	lea	(loc_290BD4).l,a0
	bsr.w	PaletteFadeTo
loc_290C5E:
	tst.w	($FFFFDEC2).l
	bne.s	loc_290C5E
	rts
```

`loc_290BD4` — это **128 байт нулей прямо в банке кода**, то есть чёрная
палитра, и `$290BD4 + 128 = $290C54` приходится ровно на процедуру,
которая её берёт. Граница сходится сама.

## Перепись палитр

```
python tools/sprites.py --pals
```

Инструмент делает две вещи и сводит их: ищет 128-байтные куски по правилу
`0BGR` (`v & $F111 == 0` у всех 64 слов) и **отдельно находит в коде пары**
«`lea $ADDR,a0`, следом `PaletteFadeTo` или `PaletteLoad`», обрывая поиск,
если `a0` между ними переписали. Без этого обрыва в список попадали куски
графики, у которых 60 слов из 64 правилу не отвечают.

Итог: **32 куска проходят правило; 13 грузят напрямую, 11 — палитры
уровней**, и `$2843EA` служит обоим — это и палитра уровня 18, и блок,
который грузит экран. Все загружаемые блоки правило проходят без осечек,
кроме одного слова `$001F` в `$1F74BE` (нечётный бит, который VDP всё равно
отбрасывает).

Отсюда и ответ на вопрос, какой палитрой красятся кадры **вне** уровня:
общего блока нет, каждый экран грузит свой перед отрисовкой.

Девять кусков правилу отвечают, но их не грузит ни один из двух путей и
указателя на них в ПЗУ нет. Двум нашлось объяснение: `$1EAC4A` — срез
поперёк трёх подряд лежащих блоков растрового разрыва
([terrain.md](terrain.md)), а `$1F747E` перекрывается наполовину с
загружаемым `$1F74BE`, то есть это тот же поток с другой привязки.
Перекрытия инструмент теперь отмечает сам.

**Остальные семь выглядят палитрами по всем доступным меркам** и не
отличаются от загружаемых ничем, кроме отсутствия загрузчика. Попытка
развести их по длиннейшему повтору провалилась, и это стоит записать:
у загружаемого `$1F80BA` повтор 48 при 16 разных цветах, а у всех
семи спорных он от 2 до 11. **Признак не различает**, и довод «случайное
совпадение исключено» был неверен ровно настолько же: правило `0BGR`
даром проходится на рядах `$0000` и `$0EEE`, которых в картридже много.
