# Движок: вход, прерывания, ядро

## Как игра стартует

| адрес | что происходит |
|---|---|
| `$2979E4` | `EntryPoint`. Проверка `$A10008`/`$A1000C` — если игра уже инициализирована, сразу на `$297ADE` |
| `$2979F4` | берётся таблица инициализации `$297A72`: `d5=$8000`, `d6=$3FFF`, `d7=$0100`, `a0=$A00000` (ОЗУ Z80), `a1=$A11100` (запрос шины), `a2=$A11200` (сброс), `a3=$C00000` (данные VDP), `a4=$C00004` (управление VDP) |
| `$297A0A` | защита TMSS: `'SEGA'` в `$A14000`, но только если в `$A10001` есть версия |
| `$297A1C` | 24 регистра VDP из той же таблицы, затем очистка VRAM, CRAM и VSRAM |
| `$297AE6` | **48 команд `nop` подряд** — задержка после инициализации VDP |
| `$297B46` | `bra.w $297F4A` — настоящее начало игры |
| `$297F4A` | `suba.l a7,a7` (стек = 0), запуск драйвера Z80, определение PAL, главный цикл |

Порядок стандартный для картриджей Sega; ничего своего в загрузке нет.

**Определение PAL.** `$297F94`: бит 0 слова состояния VDP. Если PAL —
в `$FF217E` кладётся 1 и звуку уходит команда `$1B` с аргументом 1
(вероятно, поправка темпа). Это же `$FF217E` читает обработчик кадрового
прерывания.

## Прерывания

Настоящих векторов три: сброс `$2979E4`, строчное (уровень 4) `$296976`,
кадровое (уровень 6) `$2968FE`. Остальные 61 — нули или мусор, не
попадающий даже в адресное пространство ROM.

### Кадровое, `$2968FE`

```
addq.w  #1,($FFFFE196).w        ; счётчик кадров
                                 ; при PAL ($FF217E≠0) — ожидание по $C00008
цикл 1: $FFFFE166..$FFFFE176    ; 4 слота, вызываются как есть
цикл 2: $FFFFE176..$FFFFE196    ; 8 слотов, но:
          - защита от повторного входа флагом $FF0506
          - sr = $2300, то есть прерывания РАЗРЕШЕНЫ на время вызова
```

То есть у игры два списка обработчиков кадра: короткий «жёсткий» (для
работы с VDP) и длинный «мягкий», который может занимать больше кадра и
не блокирует следующее прерывание.

### Строчное, `$296976`

Один указатель — `$FFFFE198`. По умолчанию там `$29698A`, а это `rts`.
Ставится в `$295DA6`.

## Ядро: регистрация обработчиков и ожидание кадра

| адрес | что делает |
|---|---|
| `$2967B6` | ждать смены счётчика `$FFFFE196` (ждать кадр) |
| `$2967C6` | ждать начала и конца обратного хода по биту 3 состояния VDP |
| `$2967E2` | то же, но в обратном порядке |
| `$2967FE` | добавить `a0` в **короткий** список (4 слота, `$FFFFE166`) |
| `$296822` | добавить `a0` в **длинный** список (8 слотов, `$FFFFE176`) |
| `$29684E` | добавить в длинный, если его там ещё нет |
| `$29687E` | убрать `a0` из короткого списка |
| `$2968AA` | убрать `a0` из длинного списка |
| `$2968D6` | очистить длинный список целиком |
| `$296B0C` | генератор случайных чисел; состояние — `$FFFFE14E` (32 бита) |

Списки — просто массивы длинных слов, ноль = пустой слот. Все операции
делаются под `ori.w #$0700,sr`.

## Соглашение вызовов: это компилятор, а не человек

Код собран компилятором C. Признаки:

* аргументы кладутся **на стек** (`pea $XX.w`, `move.l $8(a6),-(a7)`), а
  не в регистры;
* вызов почти всегда абсолютный длинный: `jsr ($XXXXXX).l` — 1609 из 1687;
* после вызова стек чистит вызывающий: `lea $4(a7),a7` — 402 места;
* кадр стека через `link a6` встречается **дважды на всю ROM**: компилятор
  адресуется к аргументам прямо от `a7`, а `a6` заводит только там, где
  без него нельзя.

Практическое следствие для разбора: **`pea` перед `jsr` — это аргумент**,
и его значение обычно и есть номер звука, объекта или состояния.

Отсюда же и то, зачем анализатору понадобился отдельный проход по
одиночным указателям: компилятор складывает адреса процедур в структуры
данных, и обходом по коду до них не добраться.

## Диспетчеры

**Уровень.** `$28EE0E`: индекс `$FF1B14` (слово) умножается на 4 и
берётся из таблицы `$1FCC08` — это процедура инициализации уровня. Сразу
следом по тому же индексу берётся `$1FCBAC` — **буквы названия уровня для
заставки**, по шесть байт на букву до первого отрицательного слова. На
каждую заводится объект (`$29974C`), в него пишутся место (`+$12`, на
`$100` выше настоящего), настоящее место (`+$4C`) и скрипт анимации
(`+$22` = `$1D6D80 + номер глифа * 2`). Разбор и все девять названий —
в [graphics.md](graphics.md).

## Заряд броска

Скорость снаряду задаёт не таблица готовых векторов, а **произведение
направления на величину заряда**. Величина копится в `$FF04E4`.

| адрес | что |
|---|---|
| `$FF04E4` | накопитель заряда, слово |
| `$1EABC2` | шаги прибавки: 14, 27, 42, 53 |
| `$1EABAE` | пять единичных векторов направления, формат 1.15 |

**Накопление.** `$292DFC` берёт из `$1EABC2` слово по индексу, прибавляет
к `$FF04E4` и зажимает в `$0200`.

**Направления.** В `$1EABAE` пять пар слов, и длина каждой ровно единица
(проверено: 0.9999–1.0000). Углы — 14.0, 26.6, 45.0, 63.4 и 180.0 градусов.
Второй столбец пары иногда адресуют отдельно как `$1EABB0`; это не другая
таблица.

**Запуск.** `$292C7E` зажимает величину в `$0800`, кладёт её в `$FF04E4` и
считает скорость обычным умножением в неподвижной точке — `mulu`, удвоение,
`swap` за старшим словом:

```asm
	cmpi.w	#$0800,d1
	blt.s	loc_292C88
	move.w	#$0800,d1      ; зажим величины
loc_292C88:
	move.w	d1,($FF04E4).l
	lea	($1EABAE).l,a1
	add.w	d2,d2
	move.w	($0,a1,d2.w),d3  ; косинус, 1.15
	mulu.w	d1,d3            ; направление * величина
	add.l	d3,d3            ; 1.15 -> 1.16
	swap	d3               ; старшее слово и есть ответ
	move.w	d3,$16(a0)       ; скорость по горизонтали
	move.w	($2,a1,d2.w),d3  ; синус
	mulu.w	d1,d3
	add.l	d3,d3
	swap	d3
	eor.w	d0,d3            ; d0 = 0 или -1:
	sub.w	d0,d3            ; отражение по вертикали
	move.w	d3,$18(a0)       ; скорость по вертикали
```

Пара `eor`/`sub` с маской `0` или `-1` в `d0` — обычный способ взять или не
взять обратный знак без ветвления. Вторая площадка, `$29302E`, делает то же
самое, только величину берёт из `d4`.

**Разворот.** `$2931B4` и `$2931C2` переключают бит 11 в `(a0)` — тот самый
флаг отражения по горизонтали — и, **только если бит и правда изменился**,
делают `neg.w ($FF04E4)`. Пары `bclr`/`beq` и `bset`/`bne` нужны именно для
этого: повторный вызов в ту же сторону знак не трогает.

**Затухание.** `$29FE16` при отрицательном `d2` (отскок) гасит `$5(a0)`,
обнуляет горизонтальную скорость напарника `$16(a1)`, делит заряд пополам
через `asr.w ($FF04E4)` и переводит объект на скрипт `$1DB604`. То есть
каждый отскок теряет половину силы.

**Сброс и проверка.** `$2930A4`, `$2931D0` и `$2A6034` обнуляют `$FF04E4`
(последний — вместе с `$FF21F8`); `$29FE4A` выставляет готовое значение
`$0600`; `$292FC4` и `$293080` проверяют накопитель на ноль, чтобы понять,
идёт бросок или нет.

Всего к `$FF04E4` обращаются восемнадцать раз, и все восемнадцать
объяснены: пять записей, три обнуления, разворот, затухание, предустановка
и восемь чтений.

Поля `+$16`/`+$18` записи объекта — это и есть скорость, длинным словом
сразу обе половины ([open-questions.md](open-questions.md), пункт 8).

## Заставка уровня

`$28EE02` строит её из двух частей. Сначала зовёт **процедуру мира** из
`$1FCC08` — она короткая и одинаковая по форме:

```
lea <скрипт сцены>,a1 ; bsr $28E654
lea <актёры>,a2       ; bsr $28E73A
```

Список актёров (`$28E73A`) — слово-счётчик, дальше по **двенадцать байт**:
x, y, скрипт анимации, обработчик. Координаты экранные, и почти все актёры
начинают за краем (`x = -16` или `336`), то есть входят в кадр. Списков
девять, по одному на мир, лежат в `$1EA35C`-`$1EA5D8`.

Потом на каждую букву названия заводится свой объект — см. ниже.

```bash
make levels LEVEL="--scene 7"
```

**Поправка к своду.** Вопрос «где лежит расстановка объектов уровня»
поставлен был неверно: `$1FCC08` — это не расстановка в игре, а сцена
заставки. Внутриигровые объекты берутся только из клеток карты (байт `+3`
свойств клетки), другой расстановки в данных нет.

## Пароли и меню DEBUG

Экран ввода пароля — `$29098C`. Пароль всегда **шесть букв** `A`-`Z`,
буфер ввода `$FF0016`, курсор ходит по кругу от 0 до 5.

### Пароли уровней

Таблица `$1FCB26`, семь записей по шесть байт: слово номера и длинное
слово-указатель на строку. Сравнение прямое, совпадение кладёт
`слово + 1` в `$FF1B14` и играет звук `$31`.

| пароль | уровень | куда |
|---|---|---|
| `ININJA` | 3 | NINJA TRAINING GROUNDS |
| `ILVMUD` | 7 | MUDDRAKE MAYHEM |
| `ITSHOT` | 10 | THE SACRIFICE OF MAUI |
| `GETHIM` | 12 | THE TEST OF DUCKHOOD |
| `YOHOHO` | 14 | THE FLYING DUCKMAN |
| `UNDEAD` | 16 | THE REALM OF THE DEAD |
| `GDLUCK` | 18 | MOJO STRONGHOLD |

Что разбор верен, видно без эмулятора: каждый пароль подходит своему
уровню по смыслу — `ILVMUD` к грязевым, `ITSHOT` к вулкану, `UNDEAD` к
царству мёртвых, `GDLUCK` к последнему оплоту.

### Чит на DEBUG

Два пароля вводятся **по очереди**, и хранятся они **со сдвигом на
единицу**: `$290A66` сравнивает введённую букву плюс один. `$1EAA27`
содержит `JNDBSZ`, то есть вводить надо **`IMCARY`**; после него
`$FF0010` становится 1 и проверяется `$1EAA2E` — `NBVJNN`, то есть
**`MAUIMM`**. Совпало — `$FF2180 = 1` и звук `$33`.

Дальше `$2908FA` берёт описатель главного меню по этому байту: обычно
`$1FD440` (`START`, `OPTIONS`, `PASSWORD`), а при `$FF2180` — `$1FD46E`,
где есть ещё и `DEBUG`. Так закрывается вопрос «чем выбирается вариант
меню».

В самом меню DEBUG: `ENEMY COLL` (ON/OFF), `GAME FLOW` (ON/OFF),
`MAP MODE` (OFF/ON) и выбор уровня — **23 коротких названия**, и их
порядок слово в слово повторяет таблицу уровней:

```
MOJO MANSION-1..3   N TRAINING -1..3, B   MD MAYHEM -1..3
VOLCANO -1..2       DUCKHOOD -1..2        DUCKMAN -1..2
ZOMBIES -1..2       STRONGHOLD-1          LUAU - ACT 1..4
```

Это третье независимое подтверждение, что уровней ровно 23, и заодно
перевод названий заставки на язык разработчиков: «THE SACRIFICE OF MAUI»
у них `VOLCANO`, «THE REALM OF THE DEAD» — `ZOMBIES`.

```bash
make levels LEVEL=--passwords
```

Обработчики пунктов меню лежали в `bin` (`$29080E`-`$290BB8`, 938 байт):
адреса берутся из описателей меню, обход по потоку управления туда не
доходит. Переведены в код руками, пересборка осталась побайтовой.

## Три формы игрока

Главная механика игры — смена костюма — держится на одном слове в ОЗУ,
`$FF133A`. Оно выбирает **две таблицы разом**: скрипты анимации и
обработчики действий.

| `$FF133A` | скрипты `$FF1336` | обработчики `$FF1332` | высота `$FF133C` | кто |
|---|---|---|---|---|
| 0 | `$1FCC64`, 11 | `$1FCCE0`, 46 | `$20` | Maui Mallard, утка |
| 1 | `$1FCC90`, 10 | `$1FCD98`, 46 | `$20` | Cold Shadow, ниндзя |
| 2 | `$1FCCB8`, 10 | `$1FCE50`, 46 | `$10` | уменьшенный |

Три набора скриптов лежат **встык одним куском** `$1FCC64`-`$1FCCE0`, три
набора обработчиков — так же, `$1FCCE0`-`$1FCF14`. Ставят их три
процедуры:

* `$291B60` — утка, `$291B84` — ниндзя. Обе просто пишут пару указателей
  и `$FF133A`. Зовут их со всех сторон: подбор значка превращения
  (`$2A9082`, звук `$2F`), загрузка уровня (`$2986AC` — форма
  восстанавливается), концовки этапов;
* `$29A8A0` — **переключатель** обычной и уменьшенной формы. Он же
  проигрывает превращение: кладёт в `$FFFFE1EC` скрипт `$1D7E8E`
  (уменьшиться) или `$1D7EE4` (вырасти), а это кадры 255-272 — Дональд
  сплющивается. Форму 1 он не трогает: `cmpi.w #1,d2; beq` и выход, то
  есть ниндзя уменьшаться не умеет.

Высота `$FF133C` не для красоты: её прибавляют к координате в пробе земли
(`$2A4F...`), поэтому уменьшенный Дональд и стоит, и пролезает иначе.

Что форма 1 это именно ниндзя, видно по кадрам: у формы 0 первые кадры
скриптов — 63, 94, 108 (утка в красной жилетке), у формы 1 — 431, 498, 530
(чёрное ги с красным поясом), у формы 2 — 2350 и 2413 (крошечный Дональд).

```bash
make anim ANIM=--forms
```

**Состояние игрока.** `$2A4EE0`: индекс `$FF2130` (байт) — таблица
`$1FD014`, 273 записи. Вокруг вызова видно работу с полями `+$18`
(скорость по вертикали: к ней прибавляют `$3C`, а в особом случае `$0C`)
и битами `$30(a0)`; `$FF2131` при этом сравнивается с 1, а `$FF2132`
служит набором флагов.

## Палитра: плавный переход за 16 кадров

`$290C70` принимает в `a0` палитру из 64 слов (`0BGR`, четыре ряда по 16
цветов) и запускает переход:

1. каждый цвет раскладывается по нибблам маской `$0F0F` — отдельно
   красный и зелёный+синий;
2. разница с текущей палитрой `$FFFFDC40` делится на 16 (`asr.l #4`) —
   получается шаг на кадр;
3. пары «текущее значение, шаг» ложатся в `$FFFFDCC2`;
4. в короткий список обработчиков кадра добавляется `$290CBC`, который
   16 раз (`$FFFFDEC2`) досыпает шаг и пишет CRAM командой `$C0000000`;
5. на время перехода поднят флаг `$FFFFDCC0` — главный цикл на нём ждёт
   (`$298154`).

Палитры в ROM лежат без сжатия, подряд 64 словами.

## Передачи в VRAM

Отдельная тема со своим документом: очередь DMA, разгребатель из ОЗУ,
рукопожатие со звуковым процессором и то, откуда берутся тайлы, —

## Объекты: списки, связанные словом

Адреса объектов хранятся **словами**: ОЗУ Mega Drive лежит в
`$FF0000-$FFFFFF`, поэтому `movea.w` со знаковым расширением превращает
`$E1CA` обратно в `$FFFFE1CA`. Ноль означает «конца списка нет».

* `+$2` записи — следующий в списке;
* `+$10` — ключ, по которому список держат отсортированным;
* `$295EA2` и `$295EF6` переставляют запись в списке по этому ключу,
  голова — `$FFFFE1C0`;
* `$29974C` и `$299780` создают объект: зовут `$295EA2`, потом `$2996C2`,
  и возвращают `a0` = запись либо `movea.w #0,a0` при отказе.

Что именно упорядочивает ключ `+$10` — порядок отрисовки, приоритет
обновления или что-то третье — **не установлено**.

| `$FFFFFC70` | записи анимации тайлов, по 16 байт |

Осторожно: ОЗУ переиспользуется между режимами. `$FFFFE1BE` в одном месте
работает псевдозаписью перед головой списка, а на экране `$28FB5C` — просто
счётчиком от `$20` до `$E0`.

Полная выкладка обращений — в [ram-map.md](ram-map.md), она **генерируется**
`tools/rammap.py`; правки в ней затираются.
