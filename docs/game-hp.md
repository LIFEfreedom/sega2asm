# Очки здоровья

Найдено разбором кода, подтверждено ROM. Где вывод неполный — сказано прямо.

## Как нашлось

Поиск шёл по сигнатуре «урон»: вычитание ИЗ памяти, за которым идёт
ветвление по знаку и обнуление того же адресата. По всему ROM такое место
ровно одно — `$01D22C`. Оно и оказалось входом в целый модуль HP.

## Хранение

**Текущие HP — слово по смещению `+$16` записи юнита.**

Массив юнитов: `$FF5F4E`, записи по `$30` (48) байт, индекс — байт, то есть
до 256 юнитов. Размер записи доказан явным умножением:

```asm
; $015388
	andi.w	#$00FF,d0
	mulu.w	#$0030,d0
	lea	($FF5F4E).l,a0
	adda.w	d0,a0
```

Остальной код считает то же идиомой «×48 = ×16 сохранить, ×32, сложить»:

```asm
; $017E80
	lsl.w	#4,d1
	move.w	d1,d3
	lsl.w	#1,d1
	add.w	d3,d1
	lea	($FF5F4E).l,a3
	adda.w	d1,a3
```

Опознанные поля записи:

| смещение | размер | что это |
|---|---|---|
| `+$00` | byte | тип |
| `+$02` | byte | клетка X на карте |
| `+$03` | byte | клетка Y на карте |
| `+$07` | byte | состояние (анимация) |
| `+$09` | byte | владелец: `>0` игрок 1, `<0` игрок 2, `=0` ничей |
| `+$16` | **word** | **текущие HP** |
| `+$18` | word | смещение в таблице дескрипторов `$01FC5A` |
| `+$1C` | byte | бит 0 — HP ниже первого порога, бит 1 — ниже второго |
| `+$28` | byte | битовые флаги, биты 4..7 по номеру игрока |

## Параметры: максимум и два порога

Максимум и пороги лежат не в записи, а в ROM. Путь до них одинаков в четырёх
местах кода:

```asm
	lea	($01FC5A).l,a4
	move.w	$18(a2),d7        ; готовое БАЙТОВОЕ смещение, не индекс
	lea	($0,a4,d7.w),a4
	movea.l	$0(a4),a4         ; -> блок параметров
	move.w	$4(a4),$16(a2)    ; HP = максимум
```

Значит в блоке параметров: `+$04` — максимум, `+$06` и `+$08` — пороги
(они сравниваются с текущими HP в `$01D276` и `$01D28E`).

Таблица дескрипторов `$01FC5A` — 19 записей: первые четыре с шагом `$18`,
дальше пятнадцать с шагом `$30`.

| дескриптор | блок | максимум | порог 1 | порог 2 | доля |
|---|---|---|---|---|---|
| 0–3 | `$023164` | 10000 | 1 | 1 | — |
| 4, 10 | `$02248C` | 1000 | 650 | 350 | 65% / 35% |
| 5, 11 | `$0225D2` | 1200 | 500 | 300 | 42% / 25% |
| 6, 12, 14 | `$022718` | 1800 | 700 | 300 | 39% / 17% |
| 7, 16 | `$02285E` | 2200 | 800 | 300 | 36% / 14% |
| 8, 13 | `$0229A4` | 1500 | 700 | 350 | 47% / 23% |
| 9, 18 | `$022AEA` | 1300 | 500 | 300 | 38% / 23% |
| 15 | `$022D76` | 1800 | 600 | 300 | 33% / 17% |
| 17 | `$022E3A` | 2000 | 800 | 300 | 40% / 15% |

Восемь разных наборов на пятнадцать типов — дескрипторы делят блоки
попарно. Блок `$023164` с максимумом 10000 и порогами 1/1 стоит особняком:
пороги в единицу означают, что «ранен» он бывает только при HP = 0. На него
ссылаются ровно те четыре дескриптора, что лежат с другим шагом. Что это за
сущность, я не установил — но это не динозавр.

Голова блока параметров, общая для всех восьми (на примере `$022E3A`):

| смещение | значение | что видно |
|---|---|---|
| `+$00`, `+$02` | 250, 200 | назначение не установлено |
| `+$04` | 2000 | **максимум HP** |
| `+$06` | 800 | **первый порог** |
| `+$08` | 300 | **второй порог** |
| `+$0A`, `+$0C`, `+$0E` | 800, 900, 1100 | возрастающая тройка |
| `+$10` | 2000 | ещё один предел |
| `+$12`…`+$39` | 10 пар слов | по блоку одинаковые |

## Процедуры

Весь модуль лежит подряд, `$01D1FE`–`$01D36C`.

**Урон, `$01D224`:**

```asm
	tst.w	$16(a2)
	beq.w	loc_01D240        ; уже мёртв — ничего
	sub.w	d7,$16(a2)        ; d7 — величина урона
	bhi.w	loc_01D240        ; ещё жив
	bsr.w	loc_01E8D8        ; смерть
	bsr.w	loc_01D132        ; счётчик потерь владельца
	clr.w	$16(a2)           ; пол в нуле
loc_01D240:
	move	sr,-(a7)
	bsr.w	loc_01D25C        ; пересчёт битов порогов
	rtr                       ; вернуть флаги ВЫЧИТАНИЯ, а не пересчёта
```

Пара `move sr` / `rtr` здесь существенна: она сохраняет флаги от `sub`, и
вызывающий может сразу проверить, убил ли он цель. Это даёт 9 мест вызова.

**Лечение, `$01D248`** — `add.w d7,$16(a2)` с насыщением в `$FFFF` по
переносу. Обратите внимание: насыщение идёт **не в максимум типа**, а в
`$FFFF`. Верхнего ограничения по максимуму в этой процедуре нет; есть ли
оно у вызывающих — я не проверял.

**Пересчёт порогов, `$01D25C`** — ставит или снимает биты 0 и 1 байта
`+$1C` сравнением текущих HP с `+$6` и `+$8` блока параметров.

**Класс состояния, `$01D30C`** — возвращает в `d7` одно из пяти значений:

| d7 | условие |
|---|---|
| 1 | HP = максимум |
| 2 | HP ≥ первого порога |
| 3 | HP ≥ второго порога |
| 4 | HP > 0 |
| 5 | HP = 0 |

Это и есть «шкала здоровья» — пять ступеней, а не непрерывный процент.

**Быстрые запросы:** `$01D2AC` возвращает `+$1C & 3` (степень повреждения
0..3), `$01D2BE` проверяет только бит 1 («критическое»).

## Смерть

`$01D132` — счётчик потерь. Выбирает состояние владельца по знаку `+$9` и
увеличивает слово `+$42` с потолком 999:

```asm
	tst.b	$9(a2)
	blt.w	loc_01D14C
	beq.w	loc_01D162        ; ничей — не считать
	lea	(Player1State).l,a0
	bra.w	loc_01D152
loc_01D14C:
	lea	(Player2State).l,a0
loc_01D152:
	move.w	$42(a0),d0
	cmpi.w	#$03E7,d0         ; 999
	bcc.w	loc_01D162
	addq.w	#1,$42(a0)
```

`$01D168` — предсмертный звук: `$BF` игроку 1, `$C0` игроку 2, через трап
`$FF2F`.

## Отображение

`$01D79A` берёт выбранного юнита и кладёт его класс здоровья в `+$1E`
состояния игрока:

```asm
	movea.l	(CurrentPlayerPtr).l,a1
	move.w	$1C(a1),d4        ; смещение выбранного юнита
	beq.w	loc_01D7E4        ; никто не выбран
	lea	($FF5F4E).l,a2
	adda.w	d4,a2
	...
	move.b	#$06,$1E(a1)      ; особое состояние 6
	...
	move.b	#$05,$1E(a1)      ; особое состояние 5
	...
	bsr.w	loc_01D30C
	move.b	d7,$1E(a1)        ; иначе класс здоровья 1..5
```

То есть на экране показывается не число, а одна из шести ступеней.

Класс здоровья также напрямую задаёт **состояние (анимацию) юнита** —
таблица `$01B2EC`, шесть байт плюс дополнение:

```
dc.b $0A, $18, $0A, $0E, $0E, $0E, $0E, $0E
```

Индекс — класс из `$01D30C`. Полное здоровье даёт состояние `$18`, ниже
первого порога — `$0A`, всё остальное — `$0E`.

## Связь с поведением

Побочная находка, отвечающая на прежний вопрос про логику динозавров.
В `code_137` десять мест вида:

```asm
	bsr.w	loc_01D2AC        ; степень повреждения
	bne.w	<пропустить ветку>
	...
	bsr.w	loc_01D2BE        ; критическое?
	beq.w	loc_016E9E
	lea	loc_018F02(pc),a6 ; одна процедура
	bra.w	loc_016EA2
loc_016E9E:
	lea	loc_018ED2(pc),a6 ; другая процедура
loc_016EA2:
	bsr.w	loc_018310
```

Это дерево поведения: цепочка `bsr <условие>` / `bne <выход>`, где каждая
проверка возвращает флаг Z, а здоровье — одно из условий. Раненый юнит
уходит в другую ветку, критически раненый — в третью. Само дерево
(`$016D2E`–`$0175B0`) не разобрано.
