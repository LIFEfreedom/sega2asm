# Как степень удара превращается в потерю здоровья

Недостающее звено между `ResolveCombat` и `HpDamage` найдено.

## Формула

```asm
; $01B4F8
	a4 = блок параметров НАПАДАЮЩЕГО (a2)
	moveq	#0,d5
	move.b	$15(a3),d5        ; состояние ПОЛУЧАЮЩЕГО
	cmpi.b	#$17,d5
	bhi.w	<выход>
	subi.b	#$14,d5
	bcs.w	<выход>           ; допустимы только $14..$17
	add.w	d5,d5             ; степень 0..3, ×2
	btst	#5,$11(a2)        ; нападающий улучшен?
	beq.w	loc_01B53E
	addi.w	#$00C4,d5         ; улучшенная таблица силы
	move.w	($0,a4,d5.w),d7
	bra.w	loc_01B546
loc_01B53E:
	addi.w	#$000A,d5         ; обычная таблица силы
	move.w	($0,a4,d5.w),d7
loc_01B546:
	a4 = блок параметров ПОЛУЧАЮЩЕГО (a3)
	btst	#5,$11(a3)        ; получающий улучшен?
	beq.w	loc_01B56C
	move.b	$AF(a4),d6
	bra.w	loc_01B570
loc_01B56C:
	move.b	$AE(a4),d6
loc_01B570:
	mulu.w	d6,d7
	asr.l	#8,d7             ; ← урон = сила × коэффициент / 256
	movea.l	a3,a2
	bsr.w	loc_01D224        ; HpDamage
```

**Урон = сила нападающего по степени × коэффициент цели, делённое на 256.**

Степень берётся не из поля `+$29`, а прямо из **состояния** получающего:
`$14`, `$15`, `$16`, `$17` дают индексы 0…3. Это поправка к тому, что я
написал в `docs/game-actions.md`: `+$29` там назван носителем степени, и
записывается он действительно вместе с состоянием, но в расчёте урона не
участвует. Больше того, **читателей у `+$29` в разобранном коде нет вовсе** —
четыре места пишут, ни одно не читает.

## Сила удара по степеням — `+$0A`, `+$0C`, `+$0E`, `+$10`

Раньше эти поля значились как «возрастающая тройка и ещё один предел».
Теперь ясно, что это четыре значения силы по степеням исхода.

| вид | макс HP | степень 0 | 1 | 2 | 3 (редкая) |
|---|---|---|---|---|---|
| ｽﾃｺﾞ | 1000 | 75 | 100 | 125 | **1300** |
| ﾄﾘｹﾗ | 1200 | 150 | 250 | 350 | **1800** |
| ｱﾛ | 1800 | 500 | 650 | 800 | **2000** |
| ﾃｨﾗﾉ | 2200 | 750 | 850 | 1100 | **2500** |
| ﾌﾟﾃﾗ | 1500 | 300 | 400 | 650 | **1800** |
| ﾋﾟｰﾁｬﾝ | 1300 | 50 | 75 | 100 | **2500** |

Редкая степень сравнима с полным запасом здоровья или превышает его. Это
не «сильный удар», а **почти гарантированное убийство** — и потому шанс на
неё у неулучшенного юнита равен `1/256`.

## Коэффициент цели — `+$AE`, при улучшении `+$AF`

Чем он меньше, тем меньше урона проходит.

| вид | обычный | улучшенный |
|---|---|---|
| ｽﾃｺﾞ | 240/256 | 200/256 |
| ﾄﾘｹﾗ | **155/256** | 130/256 |
| ｱﾛ | 175/256 | 150/256 |
| ﾃｨﾗﾉ | 185/256 | 167/256 |
| ﾌﾟﾃﾗ | 220/256 | 175/256 |
| ﾋﾟｰﾁｬﾝ | **255/256** | 200/256 |

Лучше всех держит удар ﾄﾘｹﾗ, хуже всех ﾋﾟｰﾁｬﾝ — тот получает почти всё.

## Распределение обычных степеней

```asm
	jsr	(Random).l
	subi.b	#$60,d0
	bhi.w	<дальше>          ; степень 0, если d0 <= 96
	...
	subi.b	#$7C,d0
	bhi.w	<дальше>          ; степень 1, если d0 <= 220
	                          ; иначе степень 2
```

| степень | доля |
|---|---|
| 0 | 97/256 = 37.9% |
| 1 | 124/256 = 48.4% |
| 2 | 35/256 = 13.7% |

## Что на самом деле даёт улучшение

Улучшение поднимает шанс редкой степени с 0.4% до 12–19% и поднимает силу
обычных степеней, но **снижает силу редкой**:

| вид | редкая обычно | редкая после улучшения |
|---|---|---|
| ｽﾃｺﾞ | 1300 | 1200 |
| ﾄﾘｹﾗ | 1800 | 1200 |
| ｱﾛ | 2000 | 1800 |
| ﾃｨﾗﾉ | 2500 | 2000 |
| ﾌﾟﾃﾗ | 1800 | 1500 |
| ﾋﾟｰﾁｬﾝ | 2500 | 1500 |

То есть улучшенный юнит бьёт ровнее: реже случается «одним ударом», но
обычные удары заметно тяжелее. Ожидаемый урон за удар:

| вид | обычно | после улучшения | рост |
|---|---|---|---|
| ｽﾃｺﾞ | 99 | 330 | ×3.3 |
| ﾄﾘｹﾗ | 232 | 467 | ×2.0 |
| ｱﾛ | 619 | 987 | ×1.6 |
| ﾃｨﾗﾉ | 853 | 1352 | ×1.6 |
| ﾌﾟﾃﾗ | 402 | 640 | ×1.6 |
| ﾋﾟｰﾁｬﾝ | 78 | 348 | ×4.4 |

Рост тем больше, чем слабее вид: слабейшие получают вчетверо, сильнейшие
в полтора раза. Улучшение подтягивает отстающих, а не усиливает лидеров.

## Таблицы B и C — урон от местности

```asm
; $01D3F0
	cmpi.b	#$32,d2           ; состояние $32
	...
	lea	$50(a4),a5        ; таблица B (или $EE при улучшении)
	...
	cmpi.b	#$0F,d2           ; состояние $0F
	...
	lea	$7C(a4),a5        ; таблица C (или $11A при улучшении)
loc_01D42E:
	move.w	$A(a2),d3
	jsr	(loc_021B2A).l    ; d7 = тип местности
	cmpi.b	#$1F,d7
	beq.w	loc_01D448
	cmpi.b	#$16,d7
	bgt.w	loc_01D458
loc_01D448:
	add.w	d7,d7
	move.w	($0,a5,d7.w),d7
	bsr.w	loc_01D224        ; HpDamage
```

Значения у вида 3, таблица B: по 2 на большинстве типов, 10 на типах 8, 9,
16, 100 на 17 и 18, 200 на 19 и **9999 на типах 11, 12, 13 и 20**. Девять
тысяч больше любого запаса здоровья в игре (наибольший — 3500), то есть эти
четыре типа местности убивают на месте. Таблица C устроена так же, но
значения втрое-впятеро выше.

Важно: урон от местности бьёт **только в состояниях `$32` и `$0F`**. В
остальных местность не вредит, а проходимость решается маской из таблиц
по приказам (см. `docs/game-ai-core.md`). Стоимость шага 99 при этом
значит «медленно», а не «нельзя».

Замечание без вывода: проверка пропускает индексы 0…22 и отдельно `$1F`,
а таблица B занимает 22 слова. Индекс 22 читает первое слово таблицы C, а
`$1F` уводит на 62 байта от начала — за пределы обеих. Убирается ли такая
местность до этого места, я не проверял.

## Заглушка `$0167C6`

Все пути «этого не должно случиться» ведут в одну процедуру: переполнение
пула слотов, индекс вида больше девяти, тип местности вне таблицы и ещё
двадцать шесть мест. Вся процедура целиком:

```asm
loc_0167C6:
	nop
	nop
	rts
```

Два `nop` и возврат — узнаваемая форма точки останова, оставленной после
отладки. Вызовов 29 штук. Выполнение после неё продолжается как ни в чём
не бывало: например, при забитом пуле слотов распределитель просто
обнуляет счётчик и выходит.
