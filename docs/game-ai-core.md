# Ядро ИИ: приказы, поиск цели, фильтры

Дополнение к [game-ai.md](game-ai.md), где разобрана структура дерева
поведения. Здесь — то, чего там не хватало: чем правила параметризованы и
как устроен поиск цели.

## Недостающее звено: приказ игрока

Разбор дерева оставлял вопрос, почему одни и те же правила у одного вида
ведут себя по-разному. Ответ: **поведение параметризовано приказом**.

`GetPlayerOrder` `$018CD6` берёт приказ владельца юнита:

```asm
	clr.w	d7
	tst.b	$9(a2)            ; владелец
	blt.w	loc_018CEE
	beq.w	loc_018CF8
	move.b	($FF9C93).l,d7    ; Player1State + $F
	bra.w	loc_018CFC
loc_018CEE:
	move.b	($FF9CE9).l,d7    ; Player2State + $F
	bra.w	loc_018CFC
loc_018CF8:
	move.b	#$08,d7           ; ничей юнит — приказ 8
```

| значение `+$F` | что означает |
|---|---|
| 0–7 | **направление** движения — это команда ﾕｳﾄﾞｳ (誘導, наведение) |
| 8 | ｼﾝｹﾞｷ (進撃, наступление); он же по умолчанию у ничьих |
| 9 | ﾊﾝｼｮｸ (繁殖, размножение) |
| `$0A` | ｼｭｳｺﾞｳ (集合, сбор) |
| `$0B` | ﾄﾂｹﾞｷ (突撃, атака) |
| `$0C` | ﾗﾝﾄｳ (乱闘, свалка) |

Привязка значений к названиям — не догадка, а два независимых совпадения.

**Первое.** `IsOrderBreed` `$018BF0` проверяет приказ ровно на 9, и именно
этот предикат выбирает порог **размножения** в `RuleBreed` (см.
[game-ai.md](game-ai.md)). Приказ 9 — это ﾊﾝｼｮｸ, второе имя в списке
`OrderNames`.

**Второе.** Приказ `$0A` читает точку `+$16`/`+$17` состояния игрока и
идёт к ней — это сбор в указанной точке, ｼｭｳｺﾞｳ, третье имя. А `$0B`
берёт **юнита** по смещению `+$18` и идёт к нему — атака на цель.

```asm
	cmpi.b	#$0A,d7
	bne.w	loc_018C98
	move.b	$16(a0),d0        ; точка сбора
	move.b	$17(a0),d1
	sub.b	$2(a2),d0
	sub.b	$3(a2),d1
	bsr.w	DeltaToDirection
	...
	cmpi.b	#$0B,d7
	bne.w	loc_018CCC
	move.w	$18(a0),d2        ; смещение назначенного юнита
	beq.w	loc_018CCC
	lea	(UnitRecords).l,a0
	move.b	($2,a0,d2.w),d0
	move.b	($3,a0,d2.w),d1
```

Оба имени попадают на свои места в порядке списка, а значение приказа
равно номеру имени плюс семь.

## Поправка: участок `+$12` блока параметров

Раньше я описал его как «10 пар слов». Неверно: это **две таблицы по пять
длинных слов**, индексируемые приказом минус 8.

| смещение | кто читает |
|---|---|
| `+$12`…`+$25` | `ReadStageParam` |
| `+$26`…`+$39` | `ReadStageParamB` |

Граница проверяется арифметикой: `5 × 4 + 5 × 4 = $28`, и `+$12 + $28`
даёт ровно `+$3A` — начало таблицы стоимости шага. Пять записей — ровно
пять приказов, 8…`$0C`.

Значения — битовые маски. У ｱﾛ приказы 8…12 дают `$0020FCFF` четырежды и
`$0021FFFF` на последнем; у ｽﾃｺﾞ разброс шире. То есть маска задаёт, что
виду при этом приказе разрешено.

## Два параметра поведения

| смещение | что |
|---|---|
| `+$A9` | шанс случайного хода, из 256 |
| `+$AA` | шанс пойти по подсказке приказа |
| `+$A8`, `+$AB` | значения для счётчика `+$26` юнита |

`+$A9` разводит виды по «целеустремлённости»:

| вид | `+$A9` | доля |
|---|---|---|
| ｱﾛ | 16 | 6% |
| ﾄﾘｹﾗ | 32 | 12% |
| ﾃｨﾗﾉ, ﾌﾟﾃﾗ | 77 | 30% |
| ｽﾃｺﾞ | 100 | 39% |
| ﾋﾟｰﾁｬﾝ | 128 | **50%** |

Аллозавр почти всегда идёт по делу, ﾋﾟｰﾁｬﾝ половину ходов делает наугад.
Это сходится с прочим: ｱﾛ и быстрее всех на открытом месте, и охотится
по фильтру видов, а ﾋﾟｰﾁｬﾝ не наносит урона в обычных исходах и считается
отдельно от обеих групп.

## Поиск цели

`ScanNeighbours` `$019398` обходит восемь соседних клеток по `UnitMap`,
начиная с текущего направления юнита:

```asm
	lea	(UnitMap).l,a0
	lea	data_141(pc),a5
	jsr	(Random).l
	btst	#0,d0
	beq.w	loc_0193B8
	lea	$01943C(pc),a5    ; ← зеркальный порядок
loc_0193B8:
	lea	(UnitRecords).l,a4
	lea	DirCellOffsets(pc),a1
	move.b	$24(a2),d2        ; начинать с текущего направления
	move.w	$A(a2),d3
	move.w	#$0007,d7         ; восемь клеток
```

Порядок обхода берётся из одной из **двух зеркальных таблиц**, и выбор
делается случайным битом:

| таблица | смещения направлений |
|---|---|
| `$019436` | +5, −4, +3, −2, +1, 0 |
| `$01943C` | −5, +4, −3, +2, −1, 0 |

То есть юнит веером осматривает окрестность, а случайный бит меняет
«рукость» веера. Без этого все юниты при равных условиях сворачивали бы в
одну и ту же сторону.

## Фильтры цели

Кандидат проверяется процедурой, адрес которой лежит в `a6`. Обёртки
подставляют конкретный фильтр:

| обёртка | фильтр | что принимает |
|---|---|---|
| `FindAnyEnemy` | `FilterAnyEnemy` | любой по `RelationTest` |
| `FindCarcass` | `FilterCarcass` | действие `$31` — падаль |
| `FindEnemyCarcass` | `FilterEnemyCarcass` | падаль плюс `RelationTest` |
| `FindByMask` | `FilterByMask` | вид не в маске `$0000DF38` |

Плюс уже разобранные в [game-ai.md](game-ai.md) `FilterPrey1` и
`FilterPrey1or2`, между которыми выбирает степень ранения.

## Действие

`DirectionToTarget` `$018DA2` даёт направление от себя к цели по
координатам `+$2`/`+$3`; если координаты совпали, направление берётся
случайно. Дальше `StepToTargetA`, `StepToTargetB` или `StepRandomThenGo`
кладут его в `+$24` и двигают.

Итого цикл правила: **найти соседа фильтром → взять направление к нему →
поставить направление → шагнуть**.

## Два поиска, а не один

Кроме обхода соседей есть **дальнобойный поиск**: `ScanAllUnits` `$01956C`
идёт по всем слотам начиная с зоны игрока 1, считает расстояние по
`+$2`/`+$3` и проверяет кандидата тем же фильтром в `a6`. Есть и обходы
по **шаблону клеток** — `ScanPatternA` и `ScanPatternB` берут форму из
таблицы и проверяют границы (координата не больше `$26`).

Таблицы направлений оказались одной группой из четырёх частей рядом:

| адрес | что |
|---|---|
| `$01694E` | смещения клеток: −80, −78, +2, +82, +80, +78, −2, −82 |
| `$016956` | приращения по X |
| `$01695E` | приращения по Y |
| `$016966` | третья часть, назначение не установлено |

## Приказ «свалка» и вступление в стычку

`IsOrderMelee` `$018BC0` проверяет приказ на `$0C` — ﾗﾝﾄｳ (乱闘). Два
правила, `RuleMeleeA` и `RuleMeleeB`, начинаются именно с него: при этом
приказе юнит ищет врага и лезет в драку.

Само вступление — `EngageNeighbour` `$018688`: берёт направление к соседу,
проверяет допустимость действия по набору `$0167F4` и записывает номер
партнёра в `+$20` юнита. Это то самое поле, которое в разборе боя
оказалось «номером партнёра по стычке», и теперь видно, кто его ставит.

## Чего я НЕ установил

- Смысл битовых масок в таблицах `+$12` и `+$26`. Видно, что они зависят
  от приказа и от вида, но что именно разрешают — нет.
- Какие ещё поля состояния игрока участвуют: `+$16`/`+$17` это точка
  сбора, `+$18` смещение назначенного юнита, но остальные не проверены.
- Роли примерно двадцати правил поведения из семидесяти.
- Что за таблица `$016966` в группе таблиц направлений.
- Смысл шаблонов клеток, по которым идут `ScanPatternA` и `ScanPatternB`.
